KABEERI — ملحق 17: معمارية الأداء والتوسع
Performance & Scalability Architecture
هذا الملحق يحدد كيف يجب أن تُبنى Kabeeri لتكون سريعة وقابلة للتوسع، مع الحفاظ على الاستقرار عند زيادة عدد:
المواقع.
الشركات.
المستخدمين.
المنتجات.
الطلبات.
ملفات الميديا.
موديولات ERP.
الرسائل.
الأحداث.
الـ workflows.
الـ AI actions.
التكاملات الخارجية.
الهدف:
بناء Kabeeri بطريقة لا تنهار عند النجاح.
1. لماذا الأداء والتوسع مهمان؟
Kabeeri ليست موقعًا واحدًا.
Kabeeri قد تصبح منصة تحتوي على:
آلاف المواقعآلاف الشركاتملايين الصفحاتملايين المنتجاتملايين الطلباتملفات كثيرةمستخدمين من شركات مختلفةERP data ضخمةKabeeri Mall public trafficAI actionsIntegration sync jobs
لذلك الأداء يجب أن يكون جزءًا من التصميم من البداية، وليس إصلاحًا لاحقًا.
2. القاعدة الرئيسية
الأداء في Kabeeri يعتمد على 7 قواعد:
1. Scope data correctly2. Cache aggressively but safely3. Queue heavy work4. Index searchable data5. Optimize database queries6. Separate public traffic from admin work where needed7. Monitor before scaling blindly

4. Multi-tenancy Strategy
4.1 V1 التوصية
لا نبدأ بتعقيد قواعد بيانات منفصلة لكل عميل.
التوصية:
Shared databaseorganization_id في الجداول المهمةcompany_id عند الحاجةsite_id عند الحاجة
4.2 لماذا Shared Database أولًا؟
لأنها:
أسهل في التطوير.
أسهل في الاختبار.
أسهل في بناء V1.
مناسبة للبداية.
تقلل تعقيد migrations.
4.3 مخاطر Shared Database
تسريب بيانات بين tenants لو scoping خطأ.
queries أبطأ مع نمو البيانات.
صعوبة عزل عملاء Enterprise.
لذلك يجب من البداية الالتزام بـ:
Tenant scopingPoliciesIndexesTesting permissions
4.4 Enterprise Isolation لاحقًا
لاحقًا يمكن دعم:
Shared database for normal customersDedicated database for enterprise tenantDedicated storage bucketDedicated queueDedicated AI mode
5. Tenant Scoping Rules
أي جدول مهم يجب أن يعرف سياقه.
5.1 أمثلة scope
organization_idcompany_idsite_iduser_id
5.2 قواعد
المحتوى يتبع Site.
الشركة تتبع Organization.
ERP يتبع Company.
Business Profile يتبع Organization/Company.
Professional Profile يتبع User.
Billing غالبًا يتبع Organization أو BillingAccount.
6. Database Performance
6.1 Indexes أساسية من V1
يجب إضافة indexes على:
organization_idcompany_idsite_iduser_idstatusvisibilityslugcreated_atupdated_atpublished_at
6.2 Composite Indexes
أمثلة مهمة:
site_id + slugsite_id + status + published_atorganization_id + statuscompany_id + statusbusiness_profile_id + statususer_id + status
6.3 Slug Uniqueness
Slug لا يكون عالميًا دائمًا.
أمثلة:
content_entries: unique(site_id, slug)business_profiles: unique(slug) أو unique(country, slug) حسب strategyproducts: unique(site_id, slug) أو unique(company_id, sku)
6.4 Avoid N+1 Queries
Kabeeri سيكون فيه علاقات كثيرة.
يجب استخدام:
eager loading.
pagination.
query scopes.
resource transformers.
6.5 Pagination Always
أي قائمة كبيرة يجب أن تكون paginated.
أمثلة:
Pages.
Posts.
Media.
Users.
Orders.
Products.
Tasks.

Audit logs.
Kabeeri Mall listings.

بعض الجداول ستكبر جدًا:

لاحقًا نحتاج:

26. أخطاء ممنوعة
26.1 لا تبني بدون indexes
خصوصًا على organization_id وsite_id وcompany_id.
26.2 لا تحمل كل البيانات مرة واحدة
أي list يجب أن يكون paginated.
26.3 لا تنفذ imports في request مباشر
استخدم jobs.
26.4 لا تعالج الصور الثقيلة في request مباشر
استخدم queue.
26.5 لا تحسب Trust Score في كل page view
استخدم precomputed scores.
26.6 لا ترسل AI tasks الطويلة في request مباشر
استخدم queue.
26.7 لا تخلط الملفات العامة والخاصة
الأمان والأداء يتأثران.
27. الخلاصة التنفيذية
Kabeeri يجب أن تبدأ بسيطة، لكن مصممة للتوسع.
القاعدة النهائية:
Start as a modular monolithScope data correctlyIndex earlyCache safelyQueue heavy workMonitor continuouslyScale only when evidence says so
بالعربي:
ابدأ بسيطًا، لكن لا تبني بطريقة تمنعك من التوسع عند النجاح.

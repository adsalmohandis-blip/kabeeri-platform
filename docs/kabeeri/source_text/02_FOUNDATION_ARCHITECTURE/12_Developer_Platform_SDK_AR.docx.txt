KABEERI — ملحق 12: منصة المطورين وSDK Architecture
Developer Platform & SDK Architecture
هذا الملحق يحدد كيف سيتعامل المطورون مع Kabeeri، وكيف سيتم بناء البلجنز، الثيمات، الموديولات، الـ connectors، AI Skills، والقوالب بطريقة منظمة وآمنة.
الهدف:
جعل Kabeeri قابلة للتوسع بواسطة مطورين وشركاء، بدون تكرار فوضى إضافات WordPress أو السماح لكود خارجي بكسر المنصة.
1. لماذا Developer Platform مهم؟
Kabeeri تستهدف أن تكون منصة وليست تطبيقًا مغلقًا.
لذلك يجب أن تسمح للمطورين ببناء:
PluginsThemesERP ModulesCommerce AppsConnectorsAI SkillsTemplatesIndustry SolutionsDeveloper Tools
لكن هذا يجب أن يتم عبر قواعد واضحة:
SDKManifestPermissionsHooks/EventsAPIsReview ProcessPackage SigningVersioningTestingDocumentationMarketplace Governance
2. المبادئ الأساسية
2.1 Core لا يتم تعديله مباشرة
المطور لا يجب أن يعدّل ملفات Core.
بدلًا من ذلك يستخدم:
Events.
Hooks.
APIs.
Services.
Extension points.
Theme overrides.
Module contracts.
2.2 كل Package له Manifest
أي Plugin أو Theme أو Module يجب أن يحتوي على ملف manifest يشرح:
الاسم.
النوع.
الإصدار.
الناشر.
الصلاحيات.
الاعتماديات.
events/hooks المستخدمة.
إعدادات التثبيت.
متطلبات Kabeeri.
2.3 الصلاحيات معلنة قبل التثبيت
أي Package يجب أن يعلن ماذا يحتاج.
مثال:
Read ordersUpdate payment statusRead customer emailCreate webhooks
2.4 لا وصول مباشر للبيانات الحساسة
أي Package يريد الوصول إلى:
finance.
payroll.
legal documents.
identity documents.
bank accounts.
API secrets.
يحتاج مراجعة وصلاحيات صريحة.
2.5 Events بدل الربط العشوائي
المطور يربط بمنطق المنصة عبر Events وListeners وليس عبر تعديل كود الـ Core.
مثال:
OrderCreated→ Payment App listener→ Accounting listener→ Notification listener

6. Service Providers

6.1 مسؤوليات Service Provider
تسجيل routes.
تسجيل migrations.
تسجيل views.
تسجيل translations.
تسجيل event listeners.
تسجيل hooks.
تسجيل settings.
تسجيل permissions.
6.2 مثال مبسط
class PaymobServiceProvider extends PackageServiceProvider{    public function registerPackage(): void    {        $this->name('paymob-payments')            ->hasSettings()            ->hasMigrations()            ->hasRoutes()            ->listensTo(OrderCreated::class, CreatePaymobPayment::class);    }}
7. Hooks & Events API
7.1 Events
Events هي الطريقة الرسمية للتكامل.
أمثلة:
ContentPublishedOrderCreatedPaymentReceivedCompanyVerifiedTaskAssignedInvoiceIssued
7.2 Hooks
Hooks تستخدم لتعديل أو إضافة سلوك في نقاط محددة.
أمثلة:
content.before_rendercontent.after_rendercheckout.before_paymentcheckout.after_paymentadmin.sidebar.itemsseo.meta.generate
7.3 Filters
تسمح بتعديل قيمة.
مثال:
seo.title.filterproduct.price.display.filter
7.4 Actions
تسمح بتنفيذ إجراء.
مثال:
order.created.actionuser.registered.action
8. Permissions API
8.1 تسجيل صلاحيات Package
كل Package يستطيع تسجيل صلاحياته:
PackagePermission::register([    'paymob.settings.manage',    'paymob.transactions.view',]);
8.2 عدم استخدام صلاحيات غير معلنة
أي Package يستخدم Permission غير مذكورة في manifest يجب أن يفشل في review.

30. الأخطاء الممنوعة
30.1 لا تجعل plugins تعدل Core
هذا سيكسر قابلية التحديث.
30.2 لا تسمح بحزم بدون manifest
الـ manifest أساس الحوكمة.
30.3 لا تسمح بحزم بدون صلاحيات معلنة
المستخدم يجب أن يعرف ما سيتم الوصول إليه.
30.4 لا تفتح Marketplace للمطورين قبل review/signing
ابدأ Official ثم Verified Partners.
30.5 لا تبني SDK معقد من V1
ابدأ بسيطًا ثم وسع.
31. الخلاصة التنفيذية
Kabeeri Developer Platform يجب أن توازن بين:
سهولة التوسعة+ أمان المنصة+ وضوح الصلاحيات+ توافق الإصدارات+ جودة المطورين+ حوكمة السوق
القاعدة النهائية:
Kabeeri يجب أن يكون قابلًا للتوسعة مثل WordPress، لكن محكومًا وآمنًا مثل منصة Enterprise.

KABEERI — ملحق 6: خريطة الأحداث ومحرك الـ Workflows
ملحق للملف الرئيسي وملاحق التأسيس والتشغيل والترابط والإصدارات والصلاحيات
هذا الملف يشرح كيف تتحرك الأحداث داخل Kabeeri، وكيف ترتبط أجزاء المنصة ببعضها عبر Events وWorkflows وAutomations.
الهدف:
جعل Kabeeri منصة مترابطة وذكية، بحيث أي حدث مهم يمكن أن يطلق إشعارًا، مهمة، Workflow، Webhook، AI Suggestion، Audit Log، أو تكامل خارجي.
1. لماذا Event Map مهم؟
Kabeeri ليس CMS منفصل عن ERP أو Marketplace أو Rabet.
كل شيء مترابط:
نشر صفحة→ يمسح Cache→ يحدث Sitemap→ يسجل Activity→ يرسل Notification→ يظهر في Report
طلب خدمة من Kabeeri Mall→ يفتح Conversation→ ينشئ Lead في CRM→ يرسل Notification لفريق المبيعات→ ينشئ Task متابعة→ يدخل في Activity Log
شركة تم توثيقها→ يظهر Verified Badge→ يتحدث Trust Score→ تظهر في Kabeeri Mall→ يرسل Notification→ يسجل Audit Log
بدون Event System، كل موديول سيبدأ يتصل مباشرة بباقي الموديولات، وهذا سيخلق فوضى وصعوبة في التطوير.
2. الفلسفة الأساسية
Kabeeri يجب أن يبنى بأسلوب:
Event-driven Modular Monolith
في البداية لا نحتاج Microservices.
لكن نحتاج أن كل موديول يتكلم عبر Events بدل الاعتماد المباشر المبالغ فيه.
القاعدة
Action happens→ Event fired→ Listeners react→ Logs/Notifications/Workflows/Webhooks run
مثال:
ContentPublished→ ClearContentCache listener→ UpdateSitemap listener→ LogActivity listener→ NotifyEditors listener→ TriggerWorkflows listener
3. الفرق بين Event وWorkflow وAutomation
3.1 Event
حدث حصل بالفعل.
مثال:
OrderCreatedInvoicePaidTaskAssignedCompanyVerified
صيغة الأحداث غالبًا Past Tense لأنها حدثت بالفعل.
3.2 Listener
كود يستمع للحدث وينفذ رد فعل محدد.
مثال:
عند OrderCreated→ SendOrderNotification→ ReserveStock→ CreateActivityLog
3.3 Workflow
سلسلة خطوات لها شروط وموافقات وحالات.
مثال:
Purchase Request→ Manager Approval→ Finance Approval→ Purchase Order→ Goods Receipt→ Supplier Bill
3.4 Automation
قاعدة بسيطة من نوع:
When X happens → If Y is true → Do Z
مثال:
When stock is below 10→ notify inventory manager
3.5 Webhook
إرسال حدث لنظام خارجي.
مثال:
OrderPaid → Send webhook to external ERP

23. Workflow Safety Rules
23.1 لا Workflow يحذف بيانات بدون Approval
أي action من نوع delete أو bulk update يحتاج approval.
23.2 كل Workflow Run يسجل Activity
لا توجد عمليات صامتة.
23.3 Workflow Versions
لا نعدل workflow مستخدم مباشرة بدون versioning.
23.4 Workflow Failures يجب أن تكون مرئية
أي فشل يظهر في:
Logs.
Notifications.
Admin dashboard.

26. Event Bus Rules
26.1 كل Event يجب أن يحمل Context
actor_user_idorganization_idcompany_id nullablesite_id nullablesubject_typesubject_idmetadata
26.2 كل Event مهم يجب أن يصل إلى Activity Log

29. الأخطاء الممنوعة
29.1 لا تستدعي Module مباشرة من Module آخر بشكل عشوائي
خطأ:
ServiceRequestController ينشئ Lead مباشرة بمنطق CRM داخله
أفضل:
ServiceRequestCreated event→ CRM listener creates Lead
29.2 لا تجعل Notifications داخل كل Controller
خطأ:
Controller يرسل notification مباشرة
أفضل:
Event → Notification Listener
29.3 لا تبني Workflows hardcoded فقط
في البداية ممكن تكون بسيطة، لكن يجب أن تكون قابلة للتحول إلى configurable workflows لاحقًا.
29.4 لا تجعل AI يطبق Workflow بدون Approval
AI يقترح، والمستخدم يوافق.
30. الخلاصة التنفيذية
Kabeeri يجب أن يحتوي على Event System قوي من البداية لأن كل شيء مترابط.
القاعدة:
كل فعل مهم → Eventكل Event مهم → Activity Logكل Event مناسب → Notificationsكل Event تجاري → Workflow/Automation محتملكل Event خارجي → Webhook محتملكل AI Action → Plan/Approval/Event/Log/Rollback
بدون هذا النظام، Kabeeri سيتحول إلى كود متشابك يصعب تطويره.

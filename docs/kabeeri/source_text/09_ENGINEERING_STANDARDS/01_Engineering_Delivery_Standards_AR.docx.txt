معايير الهندسة والتنفيذ والجودة — KABEERI
هذا الملف يضع المعايير التنفيذية التي تمنع الفوضى عند تحويل معمارية Kabeeri إلى كود Laravel حقيقي. الهدف هو أن يلتزم كل migration وmodel وAPI وpolicy وtest وrelease بنفس القواعد.
1. القاعدة الحاكمة
Build small, testable, observable, rollback-ready pieces.
لا يدخل main إلا كود يعمل، عليه tests أساسية، ولا يكسر migrations أو صلاحيات.
أي Feature جديدة يجب أن تحدد: context, permissions, logs, tests, rollback behavior, feature flag.
أي كود مولد بالـ AI يجب أن يمر بمراجعة بشرية واختبارات قبل الدمج.

4. Database Standards
كل كيان مهم يحتوي id داخلي وuuid/ulid عام عند الحاجة.
كل بيانات العميل يجب أن تكون tenant-scoped عبر organization_id أو علاقة واضحة تصل إليه.
لا نضع company_id أو role أو organization_id داخل users.
JSON يستخدم للmetadata المرنة، وليس للعلاقات الأساسية.
كل جدول حساس يحتاج activity/audit log عند العمليات المهمة.

5. API Design Standards
حتى لو بدأ V1 بواجهة Filament، يجب تجهيز APIs بنفس نمط ثابت حتى لا تتضارب الموديولات لاحقًا.
GET    /api/v1/organizationsPOST   /api/v1/organizationsGET    /api/v1/organizations/{uuid}PATCH  /api/v1/organizations/{uuid}DELETE /api/v1/organizations/{uuid}
العنصر
القاعدة
IDs
في APIs نستخدم uuid/ulid وليس id الداخلي.
Pagination
page/per_page أو cursor لاحقًا.
Errors
code, message, details, request_id.
Auth
Sanctum/API tokens مع scopes.
Rate Limits
حسب user/org/token/endpoint.
Filtering
filter[field]=value أو query params موحدة.
Sorting
sort=-created_at,name.

9. Logging & Error Handling
Activity log للأحداث العامة التي تهم المستخدم.
Audit log للأحداث الحساسة: صلاحيات، فوترة، توثيق، AI apply، package install، export.
Security event للأحداث الأمنية: login failed, token revoked, MFA changed.
كل exception مهم يجب أن يكون له request_id وربط بسياق organization/site/company عند الإمكان.
نوع الرسالة
للمستخدم
للمطور
Validation
رسالة واضحة قابلة للفهم
field, rule, input summary

لا تملك الصلاحية
permission, context, actor

12. Review Checklist قبل الدمج
هل migration لها rollback أو strategy واضحة؟
هل الجداول tenant-scoped؟
هل الصلاحيات معرفة ومختبرة؟
هل action/service يسجل activity/audit عند الحاجة؟
هل feature flag موجودة للميزة الكبيرة؟
هل توجد tests مناسبة؟
هل توجد seed/demo data إذا كانت feature مرئية؟
هل يوجد impact على Portable/Dedicated/Frontend Anywhere؟
هل يوجد أثر على Migration Center أو Marketplace؟
هل الكود المولد بالـ AI تمت مراجعته؟
13. Definition of Done
الميزة تعتبر منتهية فقط عندما:
الكود يعمل محليًا.
المستخدم يستطيع تنفيذ السيناريو الأساسي من الواجهة أو API.
Policy tests تمر.
Feature tests تمر.
لا توجد migrations مكسورة.
activity/audit logs تعمل عند الحاجة.
لا توجد صلاحيات واسعة غير مبررة.
التجربة موثقة في notes أو README صغير داخل الموديول.
تم اختبارها يدويًا مرة واحدة على الأقل.

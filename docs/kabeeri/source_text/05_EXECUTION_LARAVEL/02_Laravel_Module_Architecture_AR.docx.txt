KABEERI Laravel Module Architecture
معمارية موديولات Laravel لبناء Kabeeri Modular Monolith
هذا الملف يحول قاعدة البيانات وخريطة العلاقات إلى هيكل كود عملي داخل Laravel، بحيث يعرف المطور أو AI أين يضع كل Model وAction وPolicy وEvent وJob وFilament Resource بدون فوضى أو تكرار.
1. الهدف من الملف
• تثبيت هيكل موديولات واضح قبل كتابة كود V1.
• منع تحول Laravel إلى مجلد app ضخم بلا حدود بين Core وCMS وCommerce وERP.
• تسهيل العمل بمبدأ: migration واحد، model واحد، policy واحدة، action واحدة، resource واحدة، test واحد.
• ضمان أن التوسع لاحقًا إلى Packages وMarketplace وDedicated وPortable لا يحتاج إعادة هيكلة جذرية.
• توفير عقد ثابت بين الموديولات: Events, Actions, Contracts, Policies, Services.
2. القرار المعماري الأعلى
يبدأ Kabeeri كـ Modular Monolith داخل Laravel وليس Microservices. الهدف هو فصل منطقي واضح داخل الكود، مع الاحتفاظ بسرعة التطوير وسهولة الاختبار والنشر في المراحل الأولى.
القرار
المعنى التنفيذي
Modular Monolith
كل الموديولات داخل تطبيق Laravel واحد، لكن بفواصل واضحة في namespaces وservices وevents.
Core First
لا يبنى CMS أو Commerce أو ERP بدون Core Identity وPermissions وSites.
Event-driven Boundaries
الموديولات لا تستدعي منطق بعضها مباشرة إلا عبر Events أو Contracts أو Actions عامة.
Filament First
لوحة الإدارة في V1 تعتمد Filament لتسريع CRUD وPolicies وResources.
Package-ready
الهيكل الداخلي يمهد لاحقًا لتحويل الموديولات إلى Packages أو Marketplace extensions.

10. قواعد العلاقات بين الموديولات
• الموديول يملك Models وTables الخاصة به فقط.
• لو موديول يحتاج رد فعل من موديول آخر، يطلق Event ولا يستدعي Controller أو Service داخلي مباشرة.
• المشاركة بين الموديولات تتم عبر Contracts أو Actions عامة أو Events.
• لا يتم وضع Business Logic داخل Controllers أو Filament Resources.
• أي Action مهم يجب أن يسجل Activity أو Audit حسب الحساسية.
• أي فعل له أثر مالي أو أمني أو خصوصية يجب أن يمر عبر Policy/Permission.

14. Policy & Permission Architecture
• كل Model محوري له Policy: Organization, Site, ContentEntry, MediaAsset, Company, BusinessProfile.
• لا نعتمد على role ثابت داخل users.
• PermissionService يحسب السماح من memberships + roles + overrides + context.
• deny overrides allow.
• الصلاحيات الحساسة منفصلة: billing.manage, finance.journal.post, verification.approve, plugin.install, ai.apply_sensitive_change.
• Filament Resources تستدعي Policies ولا تتجاوزها.
// Example permission check pattern$permissionService->can(    user: $user,    permission: 'content.publish',    context: new SiteContext($site));

لأن Kabeeri context-first، يفضل إنشاء كائنات سياق صغيرة لتجنب تمرير organization_id/site_id/company_id بشكل عشوائي.

• لا تضع API عامة للبيانات الخاصة بدون scope واضح.
• الـ public APIs يجب أن تكون visibility-aware وrate-limited.
• أي API خارجية يجب أن تستخدم token scopes وrequest logging.

18. Package-ready Design
الموديولات الداخلية ليست Packages خارجية في V1، لكنها يجب أن تكون قابلة للتحول لاحقًا. لذلك يتم الالتزام بـ manifest-like metadata وdeclared permissions وevents بدلاً من تعديل Core مباشرة.

21. Anti-patterns ممنوعة
• وضع company_id أو role ثابت داخل users.
• استدعاء Service داخلي من موديول آخر بدل Event/Contract.
• Controllers تحتوي business logic.
• Filament Resources تتجاوز Policies.
• استخدام JSON بدل علاقات أساسية.
• بناء ERP أو Marketplace أو AI كامل قبل استقرار V1.
• فتح Package Marketplace بدون manifest/permissions/review/signing.
• تنفيذ imports أو media processing داخل request مباشر.
• أي Action حساس بدون Audit log.
• أي AI apply بدون plan/preview/approval/rollback foundation.
22. Checklist قبل بدء كتابة الكود
• تم اعتماد Database Master Index.
• تم اعتماد Master ERD / Relationship Map.
• تم اعتماد Laravel Migration Build Order.
• تم تحديد أول Wave من migrations.
• تم إنشاء folder structure الأساسي.
• تم تحديد أول 5 modules في V1: Auth, Organizations, Permissions, Sites, CMS.
• تم تجهيز test runner وPint.
• تم تجهيز Filament admin login.
• تم الاتفاق أن كل feature تمر بـ: migration → model → policy → action/service → UI/API → tests.
23. الخلاصة التنفيذية
هذا الملف يحوّل Kabeeri من رؤية ضخمة إلى هيكل Laravel قابل للبناء تدريجيًا. القاعدة النهائية: ابدأ Modular Monolith صغيرًا، افصل الحدود بوضوح، استخدم Events بدل التشابك، اجعل Policies وTests جزءًا من كل Feature، ولا تفتح التوسعات العامة قبل الحوكمة والأمان.

الإصدار: 1.0 — التاريخ: 4 مايو 2026 — المرحلة التالية بعد Database Master Index وMaster ERD
هذا الملف ليس قاموس بيانات جديد، بل ملف تنفيذي لترتيب بناء جداول Kabeeri في Laravel بطريقة تمنع تضارب العلاقات وتقلل إعادة البناء. يعتمد على ملفات Database السابقة، خصوصًا Core Kernel وCloud وFrontend Anywhere وPortable وDedicated وملف التكامل بين الأنظمة الخمسة وMaster ERD.
1. الهدف من هذا الملف
الهدف هو تحويل قاعدة البيانات الكبيرة إلى ترتيب عملي قابل للتنفيذ داخل Laravel Migrations. بدون هذا الملف قد يبدأ التنفيذ بجداول متقدمة قبل تأسيس الهوية والملكية والصلاحيات، مما يسبب إعادة هيكلة لاحقة.
• تحديد أول جدول يُبنى وآخر جدول يُؤجل.
• تحديد waves واضحة بدل بناء كل شيء دفعة واحدة.
• تحديد قواعد foreign keys وnullable وindexes وUUID/ULID.
• منع التكرار بين الملفات: billing، media، audit، sync، settings.
• تجهيز V1 للتنفيذ بدون إدخال ERP/AI/Mall كامل قبل وقته.
• تسهيل العمل مع AI code generation عبر تعليمات ثابتة لا تتغير كل مرة.
2. القاعدة الحاكمة
كل migration يجب أن يجيب على أربعة أسئلة قبل كتابته:
• هل الجدول Global أم Tenant-scoped؟
• هل يحتاج organization_id أو site_id أو company_id؟
• هل سيُصدّر في Portable أو Dedicated migration؟
• هل هذا الجدول Source of Truth أم Mirror/Cache/Derived؟
أي جدول لا يجيب على هذه الأسئلة لا يدخل التنفيذ.

4. المعايير القياسية للأعمدة
الجدول التالي يمثل القالب القياسي لأي Business Entity مهم في Kabeeri. لا يلزم استخدام كل الأعمدة في كل جدول، لكن يجب عدم مخالفة الفلسفة العامة.

متى يستخدم؟

5. قواعد UUID / ULID
• الأفضل استخدام ULID بطول 26 حرفًا للكيانات الجديدة لأنه sortable ومناسب للروابط العامة.
• يجب وجود unique index على uuid في الجداول المهمة.
• لا تستخدم uuid كـ foreign key داخلي إلا عند الحاجة في sync أو external references.
• في Portable وMall Sync، يجب الحفاظ على UUIDs وعدم إعادة توليدها أثناء التصدير.
• أي public API أو webhook payload يستخدم uuid وليس id.

7. استراتيجية Nullable
• organization_id غير nullable في Tenant Tables بعد مرحلة التأسيس.
• company_id nullable لأن بعض المواقع أو المحتوى قد يتبع Organization فقط.
• site_id nullable في جداول الشركة/ERP لأنها لا تعتمد دائمًا على موقع.
• billing_account_id nullable في البداية ثم يثبت بعد إنشاء billing flow.
• external_id nullable في البداية ثم يملأ عند الربط بتكامل خارجي.
• deleted_at nullable فقط للجداول التي تقبل soft delete.

11. قواعد تسمية ملفات Laravel Migrations
• استخدم أسماء واضحة: create_organizations_table وليس create_orgs_table.
• لا تجمع أكثر من جدولين مرتبطين جدًا داخل migration واحد إلا pivot صغير.
• أسماء pivot تكون مفهومة: role_permission وليس permission_role إذا تم اعتمادها مبكرًا.
• أي migration لتعديل لاحق يجب أن يشرح السبب في اسم الملف: add_visibility_to_business_profiles_table.
• لا تستخدم أسماء مبهمة مثل create_core_tables أو update_fields.
12. أمثلة Laravel Schema Patterns
النماذج التالية إرشادية لاستخدام نفس الأسلوب في كل migration.
Schema::create('organizations', function (Blueprint $table) {
$table->id();
$table->ulid('uuid')->unique();
$table->foreignId('owner_user_id')->constrained('users')->restrictOnDelete();
$table->string('name');
$table->string('slug')->unique();
$table->string('account_type', 50)->default('business')->index();
$table->string('status', 50)->default('active')->index();
$table->foreignId('country_id')->nullable()->constrained('countries')->nullOnDelete();
$table->string('locale', 10)->default('ar');
$table->string('timezone', 64)->default('Africa/Cairo');
$table->json('settings')->nullable();
$table->json('metadata')->nullable();
$table->timestamps();
$table->softDeletes();
});
نمط Tenant Table:
$table->foreignId('organization_id')->constrained()->cascadeOnDelete();
$table->foreignId('company_id')->nullable()->constrained()->nullOnDelete();
$table->foreignId('site_id')->nullable()->constrained()->nullOnDelete();
$table->string('status', 50)->default('draft')->index();
$table->string('visibility', 50)->nullable()->index();
$table->index(['organization_id', 'status']);
$table->index(['organization_id', 'created_at']);

17. Migration Anti-patterns ممنوعة
• ممنوع إضافة company_id أو organization_id أو role داخل users.
• ممنوع بناء ERP قبل company_memberships وpermissions وactivity_logs.
• ممنوع بناء AI apply actions قبل approvals وaudit logs وrollback points.
• ممنوع Mall يقرأ من جداول العميل مباشرة؛ لازم Mall Mirror.
• ممنوع حفظ API keys أو tokens أو credentials plain text.
• ممنوع استخدام JSON بدل جداول علاقات أساسية مثل memberships أو roles.
• ممنوع جدول واحد ضخم اسمه settings يحل محل configuration المنظمة كلها.
• ممنوع حذف audit logs أو ledger records بـ cascade من جدول user.

20. Checklist قبل كتابة أول Migration
• تثبيت Laravel version وPHP version وMySQL version.
• تحديد ULID أم UUID وتنفيذ helper موحد.
• تثبيت timezone الافتراضي Africa/Cairo واللغة الافتراضية ar.
• تحديد أسماء permissions الأولى.
• تحديد أول roles system.
• تحديد هل softDeletes يستخدم في كل جدول أم حسب النوع.
• تثبيت conventions للأعمدة: status, visibility, metadata, created_by, updated_by.
• إنشاء tests للموجة الأولى قبل التوسع.
21. الخلاصة التنفيذية
ابدأ صغيرًا لكن لا تبدأ ضيقًا. أول migrations يجب أن تبني نواة تسمح بـ CMS + Company OS + Future Commerce + Future ERP + Cloud/Portable/Dedicated بدون إعادة بناء. لا تدخل أي موجة متقدمة قبل ثبات الموجات التي تعتمد عليها.
الملف التالي بعد هذا يجب أن يكون Laravel Module Architecture، لأنه سيحوّل هذه الموجات إلى مجلدات Models / Policies / Actions / Services / Events / Jobs / Filament Resources / Tests.

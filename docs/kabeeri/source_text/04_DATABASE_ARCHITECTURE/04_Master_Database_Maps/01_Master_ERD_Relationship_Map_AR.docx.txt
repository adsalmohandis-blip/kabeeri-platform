2. القاعدة العليا للعلاقات
كل جدول مهم داخل KABEERI يجب أن يجيب على أربعة أسئلة قبل بنائه:
• يتبع أي Organization؟
• يتبع أي Company أو Site عند الحاجة؟
• من يملك حق القراءة والكتابة عليه؟
• هل يمكن تصديره أو مزامنته أو ظهوره في Mall؟
أي علاقة لا تستطيع الإجابة على هذه الأسئلة تصبح خطرًا معماريًا لأنها قد تؤدي إلى تسريب بيانات أو صعوبة تصدير أو تضارب في Portable/Dedicated.

6. Organization Relationship Map
Organization هي نقطة الربط الرئيسية بين الهوية، الاشتراك، المواقع، الشركات، التصدير، أنماط التشغيل، والـ Mall participation.
ORGANIZATIONS  |- organization_memberships  |- companies  |   |- company_memberships  |   |- business_profiles  |   |- verification_requests  |   |- employee_profiles / ERP data  |- sites  |   |- cms content  |   |- commerce store  |   |- cloud_sites / frontend_projects  |- billing_accounts  |   |- subscriptions  |   |- entitlements  |- organization_operating_modes  |- business_passports  |- export_jobs / dedicated_tenants / self_hosted_installations
قاعدة مهمة: لا يتم بناء أي Module جديد بدون organization_id أو علاقة واضحة بكيان يملك organization_id.

Rabet لا يساوي Mall. Rabet مسؤول عن الهوية والثقة والتوثيق. Mall مسؤول عن الظهور العام والاكتشاف والطلبات العامة.
9. Mall Mirror Relationship Map
MALL_SYNC_SOURCES  |- mall_sync_events  |- mall_sync_errors  |- mall_mirror_businesses      |- mall_mirror_services      |- mall_mirror_products      |- mall_mirror_talent      |- reviews      |- moderation_cases      |- disputes      |- featured_listing_orders
القاعدة
التفسير
Mall لا يقرأ مباشرة من قاعدة العميل
يقرأ من Mall Mirror فقط.
Consent قبل النشر
أي business/service/product/talent يحتاج publication consent.

21. Anti-patterns ممنوعة
• إضافة users.company_id أو users.role.
• جعل Mall يقرأ من جداول Commerce أو ERP مباشرة.
• خلط فواتير Kabeeri للعميل مع فواتير العميل لعملائه.
• وضع بيانات payroll أو finance أو legal docs في public mirrors.
• الاعتماد على IDs الداخلية في sync بين Portable/Dedicated وCentral.
• تنفيذ AI changes مباشرة بدون plan/preview/approval/rollback.
• بناء search أو BI كمصدر الحقيقة بدل أن تكون derived/cached.
• تكرار documents/media في كل Module بدل media_assets/document_records المركزية.
22. Checklist قبل Laravel Migration Build Order
☐ تثبيت naming convention: plural snake_case للجداول وPascalCase للـ Models.
☐ تحديد كل جدول: global أم tenant-scoped أم mirror أم derived.
☐ تحديد organization_id / company_id / site_id لكل جدول يحتاج scoping.
☐ تحديد UUID/ULID لكل كيان يحتاج public API أو export أو sync.
☐ تحديد الجداول التي تستخدم soft deletes.
☐ تحديد الجداول الحساسة التي تحتاج audit_logs.
☐ تحديد indexes الأساسية قبل أول migration.
☐ تحديد العلاقات nullable في V1 التي ستصبح required لاحقًا.
☐ تحديد export registry لكل Module.
☐ تحديد feature flags لكل Module قبل بناء UI.
23. الخلاصة التنفيذية
هذا الملف يثبت أن KABEERI يجب أن يبنى من Organization-first architecture، وليس Site-first architecture. الموقع قناة، الشركة كيان تجاري، البروفايل واجهة عامة، والـ Mall Mirror نسخة عامة مشتقة، بينما Core Kernel هو مصدر الهوية والملكية والصلاحيات.
بعد هذا الملف، الخطوة التنفيذية الصحيحة هي كتابة KABEERI Laravel Migration Build Order لتحويل هذه العلاقات إلى موجات migrations قابلة للبناء والاختبار تدريجيًا.

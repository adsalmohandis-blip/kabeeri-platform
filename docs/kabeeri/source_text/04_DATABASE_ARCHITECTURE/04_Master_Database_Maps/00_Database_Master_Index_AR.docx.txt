7. قرارات توحيد مهمة قبل بناء migrations
هذه القرارات تمنع تكرار الجداول بين الموديولات. عند التعارض، المصدر المذكور هنا هو المرجع الأعلى.
النقطة
قرار التوحيد
Billing in Cloud vs Billing file
يجب اعتبار ملف Billing & Subscriptions هو المصدر الرئيسي. جداول Cloud billing في ملف Cloud كانت foundation أولية وتحتاج توحيد naming مع ملف Billing.
Media vs Documents
Media Library للصور والملفات العامة/الخاصة. Document Management للمستندات القانونية والتشغيلية ذات صلاحيات وسجلات وصول أقوى. لا نكرر الملفات.
Notifications in Core vs Notification Center
جدول notifications الأساسي في Core هو foundation. ملف Notification Center يوسع delivery, preferences, templates, inbox.
Audit logs in Core vs Security
audit_logs الأساسية في Core. ملف Security يضيف sensitive access, incidents, privileged access, API/security events.
Mall Mirror in Integration vs Mall file
الجداول mirror يجب أن تكون في Central/Mall domain، لكن مصدر sync معرف في Integration. لا يقرأ Mall من DB العميل مباشرة.
Reviews in Mall/Talent/Commerce
Reviews engine هو المصدر المركزي للتقييمات والسمعة. الموديولات تربط reviews عبر subject_type/subject_id.
Approvals in ERP vs Workflows
الموافقات التشغيلية في ERP تستخدم Workflow/Approval engine المركزي بدل جداول منفصلة لكل موديول.
Reports in ERP vs BI/Data Platform
التقارير التشغيلية البسيطة داخل ERP، لكن التقارير الثقيلة والـ dashboards والـ KPI في BI/Data Platform.
AI suggestions in multiple modules
AI-specific storage يجب أن يبقى في AI Co-builder، والموديولات تحفظ فقط references أو applied change links.

10. قواعد عامة لأسماء الجداول والحقول
أسماء الجداول بصيغة الجمع وsnake_case: users, organizations, business_profiles.
أسماء الموديلات بصيغة المفرد وPascalCase: User, Organization, BusinessProfile.
كل كيان business مهم يفضل أن يحتوي: id, uuid, organization_id, status, visibility, metadata, created_by, updated_by, timestamps, deleted_at عند الحاجة.
id للعلاقات الداخلية السريعة، وuuid/ulid للتصدير، الـ API، والمزامنة بين Cloud/Portable/Dedicated.
لا نستخدم JSON بدل العلاقات الأساسية. JSON فقط للإعدادات المرنة، metadata، provider-specific data، أو rules قابلة للتغيير.
أي بيانات قابلة للظهور العام يجب أن تحتوي visibility/publication_status أو تمر عبر consent/mirror layer.
أي جدول يحتوي بيانات حساسة يجب أن يرتبط بـ audit_logs أو sensitive_access_logs حسب مستوى الخطر.
11. قواعد الـ Tenancy والعزل
النمط الافتراضي في البداية: Shared Database + Tenant Scoping.
كل بيانات العميل يجب أن تحتوي organization_id مباشرة أو يمكن الوصول إليها عبر علاقة واضحة تحتوي organization_id.
site_id لا يغني عن organization_id في الجداول المهمة إذا كان الجدول يحتاج export أو billing أو audit.
company_id يستخدم عندما يكون الكيان تابعًا لشركة، وليس مجرد موقع.
Dedicated لا يلغي organization_id؛ يبقى موجودًا لتوحيد الكود ودعم multi-company داخل العميل الكبير.
Portable export يعتمد على organization_id + UUID preservation + export registry.
12. قواعد Visibility / Privacy / Public Mirror
لا يظهر أي شيء في Mall بدون mall_publication_consent.
Mall لا يقرأ من قاعدة بيانات العميل مباشرة؛ يعتمد على mall_mirror_* tables.
Frontend Anywhere لا يرى إلا public API scopes ولا يحصل على private invoices أو accounting أو employee data.
Talent Marketplace يستخدم Professional Profile منفصل عن Employee Profile الداخلي.
Reviews العامة لا تساوي performance evaluations الداخلية.
Search العام يستخدم public index فقط، أما admin search فيجب أن يكون permission-aware.
13. قواعد Events / Workflows / Audit
Action happens→ Event fired→ Listeners run→ Activity/Audit log created→ Notifications/Workflows/Webhooks triggered→ Optional AI suggestion / approval / rollback point
لا تربط الموديولات ببعض مباشرة إذا كان Event يكفي.
أي Action حساس يجب أن يترك audit log: permissions, billing, finance, verification, AI apply, package install, export, sync.
الموافقات المركزية يجب أن تمر عبر Workflow/Approval engine بدل جداول مختلفة في كل موديول.
AI لا يطبق تغييرات مؤثرة إلا عبر plan/preview/approval/apply/rollback.
14. قواعد Billing وEntitlements
ملف Billing & Subscriptions هو source of truth للخطط والاشتراكات والحقوق التجارية.
Cloud Database يحتوي روابط cloud provisioning، لكنه لا يجب أن يكرر منطق billing كامل.
Platform invoices منفصلة عن invoices التي يصدرها العميل لعملائه داخل ERP/Commerce.
أي ميزة مدفوعة يجب أن تمر عبر EntitlementService قبل التنفيذ.
Usage records يجب أن تكون قابلة للربط بـ organization/site/company/subscription/source.

16. مخاطر يجب منعها قبل التنفيذ
إنشاء users.company_id أو users.role سيكسر نموذج الصلاحيات المتعدد.
خلط Business Profile مع Company سيجعل Mall وRabet غير واضحين.
خلط Platform billing invoices مع customer invoices سيخلق مشاكل محاسبية.
قراءة Mall من DB العميل مباشرة ستكسر الخصوصية وPortable/Dedicated.
تخزين API keys أو credentials plain text في قاعدة البيانات ممنوع.
استخدام JSON لعلاقات أساسية مثل products أو companies داخل user خطأ معماري.
إدخال ERP Pro أو GRC أو Industry Suites قبل Core/CMS/Commerce/Rabet/Billing سيؤخر V1 بلا داعي.

هذا الملف يصف طبقة Enterprise Architecture & App Portfolio داخل Kabeeri كطبقة حوكمة عليا فوق Core وCloud وERP وIntegration Hub وBI وGRC وSecurity، ويهدف إلى معرفة: ما الأنظمة الموجودة؟ من يملكها؟ ما البيانات التي تديرها؟ كيف تتكامل؟ وما أثر أي تغيير قبل تنفيذه؟
1. تعريف Enterprise Architecture / App Portfolio
Enterprise Architecture / App Portfolio في Kabeeri هي طبقة تسجيل وتحليل وحوكمة للمنصة والتطبيقات والتكاملات والبيانات والقدرات التجارية. هذه الطبقة لا تبني CMS أو ERP جديدًا، بل تصف وتربط كل ما تم بناؤه حتى يمكن التحكم فيه على مستوى Enterprise.
Application Portfolio: سجل التطبيقات والموديولات والأنظمة المستخدمة داخل مؤسسة العميل أو داخل Kabeeri نفسها.
System Catalog: كتالوج الأنظمة والبيئات والمكونات والتقنيات.
Integration Map: خريطة التكاملات بين الأنظمة والـ APIs والـ webhooks والـ sync jobs.
Business Capability Map: خريطة القدرات التجارية وربطها بالتطبيقات والموديولات والفرق.
Data Ownership Map: خريطة مالكي البيانات، Data Stewards، ومصدر الحقيقة لكل مجال بيانات.
Change Impact Analysis: تحليل أثر التغيير قبل تنفيذ تغييرات على نظام أو API أو جدول أو عملية.
2. لماذا نحتاج هذا الملف؟
عند الوصول إلى V6، تصبح Kabeeri منصة واسعة تشمل ERP وBI وGRC وSecurity وDeveloper Marketplace وIndustry Solutions وIntegration Hub. بدون سجل معماري واضح، سيصبح من الصعب معرفة الاعتماديات والتكاملات ومن يملك البيانات وماذا قد ينكسر عند أي تغيير.
منع فوضى Enterprise Modules عند توسع المنصة.
مساعدة Enterprise Admin وArchitect وData Manager على فهم المشهد الكامل.
تسهيل عمليات migration من Cloud إلى Dedicated أو Portable أو العكس.
ربط GRC وSecurity وBI وIntegration Hub بخريطة واحدة.
تسريع تحليل أثر التغيير قبل تحديث API أو تعديل جدول أو استبدال Connector.
تجهيز المنصة لمراجعات Enterprise وAudit وDue Diligence.
3. القاعدة الرئيسية
هذه الطبقة Read/Analyze/Govern أكثر من كونها Transactional. أي أنها لا تحل محل الأنظمة الأصلية، ولا تصبح مصدر الحقيقة للطلبات أو الفواتير أو المخزون، بل تسجل وصفًا معماريًا ومؤسسيًا لهذه الأنظمة والبيانات والتكاملات.
Source of Truth للبيانات التشغيلية يبقى في النظام الأصلي: CMS / Commerce / ERP / Mall / Integration Hub.
Enterprise Architecture يسجل metadata وrelationships وownership وimpact.
يجب أن تكون الجداول tenant-scoped عبر organization_id.
يجب أن تدعم Cloud وDedicated وPortable، مع اختلاف مكان البيانات التشغيلية.
لا يتم تخزين secrets أو credentials هنا؛ فقط references إلى Vault أو Integration Hub.

5. ما الذي لا يدخل؟
لا يخزن بيانات ERP التشغيلية مثل journal entries أو invoices أو payroll.
لا يخزن credentials أو API secrets.
لا ينفذ sync jobs بنفسه؛ Integration Hub هو المسؤول.
لا يحل محل GRC لكنه يغذيه بمعلومات الأنظمة والاعتماديات.
لا يحل محل BI لكنه يوفر business glossary وownership وlineage foundation.
لا يفتح Public Developer Marketplace؛ هو فقط يصف المكونات المعمارية.

18. Flow: تسجيل تطبيق جديد
Enterprise Architect أو Platform Admin يفتح Application Portfolio.
ينشئ enterprise_application مع النوع والحالة والحرجية.
يربط التطبيق بالنظام الرئيسي enterprise_system إن وجد.
يحدد business owner وtechnical owner وdata owner.
يربط التطبيق بالقدرات التجارية business_capabilities.
يسجل البيانات التي يملكها أو يقرأها data_entities.
يسجل التكاملات المعروفة system_integrations.
ينشئ architecture review إذا كان النظام جديدًا أو عالي الخطورة.
تسجل activity/audit events.
19. Flow: Change Impact Analysis
المستخدم يطلب تغييرًا: API change أو schema change أو connector replacement أو package update.
create change_impact_assessment.
النظام يقرأ system_dependencies وsystem_integrations وdata_ownership_assignments.
ينشئ change_impact_items لكل تطبيق أو تقرير أو workflow أو integration متأثر.
إذا كان impact_level high أو critical، يتطلب architecture_review وapproval.
بعد الموافقة، يمكن تنفيذ التغيير عبر workflow أو deployment plan.
تسجل النتائج والـ rollback plan في audit logs.
20. Flow: Data Ownership Review
Data Manager يفتح data_domains.
يراجع data_entities وتصنيفها.
يحدد source_of_truth لكل entity.
يعين data owner وdata steward.
يربط الكيان بالتقارير والتكاملات المتأثرة.
أي change على source_of_truth يتطلب impact analysis.
تظهر ownership في BI/Data Dictionary وGRC evidence عند الحاجة.
21. Cloud / Frontend Anywhere / Portable / Dedicated
الوضع
كيف تظهر Enterprise Architecture؟
Cloud
الأنظمة والتطبيقات والبيانات داخل Kabeeri Central؛ يمكن تحليل الاعتماديات مباشرة من metadata والأحداث.
Frontend Anywhere
الواجهة الخارجية تسجل كنظام أو system environment منفصل، بينما مصدر البيانات يبقى Cloud.
Portable
التطبيق الخارجي يسجل كـ enterprise_system من نوع portable_self_hosted، والتكاملات معه عبر mall sync أو support/update channels.
Dedicated
البيئة المخصصة تسجل كـ enterprise_system + environments + components، مع ربط health/update/security/billing summaries.
External ERP/SaaS
يسجل كنظام خارجي ويرتبط عبر Integration Hub ولا تحفظ أسراره داخل هذا النظام.

25. Validation Rules
لا يوجد enterprise_application بدون organization_id إلا إذا كان platform-level مصرحًا.
لا يوجد mission_critical system بدون owner_user_id وcriticality وhealth status.
أي integration active يجب أن يكون له source_system_id وtarget_system_id.
أي data_entity sensitive أو restricted يجب أن يكون له data owner أو steward.
أي change_impact_assessment high/critical لا يكتمل بدون rollback_plan.
لا يسمح بحفظ secrets داخل path أو metadata أو endpoint fields.
أي dependency blocking يجب أن يظهر في impact analysis.
أي deprecated application يجب أن يكون له replacement أو retirement notes.

30. AI Assistants داخل Enterprise Architecture
AI Impact Assistant: يقترح impacted systems بناءً على dependency map.
AI Data Ownership Assistant: يقترح data owner/steward عند وجود فجوات.
AI Integration Mapper: يقرأ sync logs ويقترح integration map draft.
AI Portfolio Cleanup Assistant: يحدد duplicate applications أو deprecated systems.
AI Architecture Reviewer: يراجع ADR ويطلب missing rollback/security notes.
أي اقتراح AI هنا لا يطبق تغييرات مباشرة. يجب أن ينتج suggestion أو draft ثم يمر بمراجعة بشرية إذا كان يؤثر على systems أو data ownership أو critical dependencies.
31. Export / Portable / Dedicated Rules
Cloud: يمكن تصدير portfolio metadata ضمن export registry إذا وافق العميل.
Portable: يتم تصدير enterprise_applications وsystem catalog الخاصة بالعميل، مع إزالة references الخاصة بـ Kabeeri Central إذا لم تعد صالحة.
Dedicated: يتم نقل system catalog إلى البيئة المخصصة أو إبقاء نسخة bridge في Central حسب العقد.
Frontend Anywhere: تسجل الواجهة الخارجية كنظام أو environment، لكن DB source يبقى Cloud.
لا يتم تصدير أي secrets أو vault references الحقيقية؛ فقط masked references أو setup instructions.
32. Security & Compliance Requirements
تسجيل كل تغييرات ownership وcriticality وdependencies في audit_logs.
حماية cost data وsystem criticality بصلاحيات منفصلة.
منع public exposure لأي system endpoint حساس.
ربط sensitive data domains بـ Security data classification.
ربط critical systems بـ GRC controls وrisk register.
إلزام architecture review للتغييرات high/critical.
عدم حفظ credentials أو tokens أو secrets داخل metadata.

35. الخلاصة التنفيذية
Enterprise Architecture / App Portfolio Database هي طبقة الوعي المؤسسي داخل Kabeeri. بدونها ستظل المنصة قادرة على التشغيل، لكنها ستفقد القدرة على إدارة التعقيد Enterprise: من يملك التطبيق؟ ما النظام الذي يعتمد على الآخر؟ ما البيانات التي يجب حمايتها؟ وما الذي سيتأثر عند التغيير؟
القاعدة النهائية: لا تجعل Enterprise مجرد مزيد من الموديولات؛ اجعلها خريطة تحكم وفهم للتطبيقات والأنظمة والبيانات والتكاملات والتغيير.

KABEERI Database File 37
Data Warehouse / Data Platform Database
نظام مستودع البيانات ومنصة البيانات — KABEERI
هذا الملف يصف قاعدة البيانات الخاصة بطبقة Data Warehouse / Data Platform داخل Kabeeri، وهي الطبقة التي تجمع البيانات التحليلية من CMS وCommerce وERP وMall وAI وBilling وIntegration Hub لتقديم تحليلات Enterprise بدون الضغط على قواعد التشغيل اليومية.
الهدف ليس استبدال قواعد البيانات التشغيلية، بل بناء طبقة تحليلية مشتقة، قابلة لإعادة البناء، محكومة بالصلاحيات، وقابلة للتوسع مع Cloud وDedicated وPortable.
1. تعريف Data Warehouse / Data Platform
Data Warehouse هو مستودع بيانات تحليلي مركزي أو شبه مركزي يحتوي على نسخ مشتقة ومنظمة من البيانات التشغيلية، ويستخدم للتقارير الثقيلة، مؤشرات الأداء، التحليلات التاريخية، المقارنات الزمنية، ومخرجات BI/AI.
Data Platform هي الطبقة الأوسع التي تشمل مصادر البيانات، عمليات الاستخراج والتحويل والتحميل، قاموس البيانات، جودة البيانات، المارتات التحليلية، الكتالوج، قواعد الملكية، والربط مع أدوات BI خارجية.
هذه الطبقة تظهر بوضوح في V6 مع BI / Analytics / Data Platform، لكنها يجب أن تُصمم منذ V5 كامتداد آمن لـ Advanced Reporting Foundation.
2. لماذا نحتاج ملف Database مستقل؟
التقارير الثقيلة لا يجب أن تعمل مباشرة على جداول التشغيل مثل orders أو journal_entries أو stock_movements.
الـ dashboards تحتاج cached snapshots حتى لا تتأثر تجربة المستخدم.
KPI calculations يجب أن تعمل كـ jobs مجدولة، وليس داخل request مباشر.
Enterprise تحتاج Data Dictionary وBusiness Glossary حتى يفهم المستخدمون معنى الحقول والمؤشرات.
البيانات القادمة من Cloud وDedicated وPortable تحتاج مصدر موحد للتحليل مع احترام العزل والخصوصية.
AI Report Explainer وAI Data Quality Assistant يحتاجان طبقة بيانات منظمة وآمنة.

4. مبادئ تصميم قاعدة بيانات Data Platform
المبدأ
التطبيق
Derived, not Source of Truth
المستودع مشتق من قواعد التشغيل. إذا تلف أو احتاج إعادة بناء، يمكن إعادة توليده من المصادر الأصلية.
Tenant-aware
كل سجل تحليلي يجب أن يعرف organization_id، وعند الحاجة company_id/site_id، حتى في Dedicated.
Permission-aware Analytics
لا يكفي وجود البيانات؛ يجب احترام صلاحيات المستخدم عند عرض dashboards أو export.
Historical Snapshots
التقارير تحتاج snapshots زمنية لا تتغير بتغير البيانات التشغيلية لاحقًا.
Job-based Processing
التحميل والتحويل والتجميع يتم عبر queued jobs وليس داخل request.
Data Quality by Design
كل dataset مهم يجب أن تكون له quality rules وvalidation results.
Portable/Dedicated Safe
لا يتم سحب بيانات حساسة من Portable/Dedicated إلا بعقد sync واضح وموافقة.

34. Cloud / Frontend Anywhere / Portable / Dedicated
الوضع
سلوك Data Platform
Cloud
أفضل وضع للتحليل لأن البيانات التشغيلية داخل Kabeeri، ويتم ingestion داخليًا من نفس البيئة أو read replica.
Frontend Anywhere
لا يتغير مصدر البيانات؛ الواجهة خارجية فقط، والتحليلات تعتمد على Cloud DB ومصادر public API logs.
Portable
التحليلات المركزية لا تسحب بيانات تشغيلية إلا إذا فعّل العميل connector/scheduled export؛ Mall analytics قد تستمر من mirror فقط.
Dedicated
يمكن تشغيل Data Platform داخل البيئة المخصصة أو إرسال aggregates فقط إلى Central حسب العقد وData Residency.
35. Privacy & Security Rules
لا يتم إدخال payroll أو salary أو identity documents في analytics إلا بتصنيف عالي وصلاحيات صريحة.
أي external BI export يجب أن يمر عبر data_access_policies وexport approvals إذا كان حساسًا.
AI analytics contexts يجب أن تستخدم redaction/minimization قبل إرسال أي context لمزود خارجي.
Data dictionary يجب أن يحدد classification لكل field حساس.
Warehouse query logs يجب أن تسجل من استخرج ماذا ومتى.
لا يتم إعطاء direct SQL access للمستخدم النهائي في V1/V5؛ report builder يستخدم طبقة آمنة.
36. Performance Rules
Data warehouse jobs يجب أن تكون queued ومجزأة.
Heavy reports queued، ولا تعمل داخل request مباشر.
Dashboard caching إلزامي للـ executive dashboards.
KPI calculation jobs مجدولة ويمكن إعادة تشغيلها.
Aggregations scheduled حسب المجال والباقة.
Large exports تعمل كـ job مع رابط تحميل مؤقت.
يفضل استخدام read replicas أو dedicated analytics database في V6.

41. Acceptance Criteria
يمكن تعريف data source داخلي لموديول Commerce أو ERP.
يمكن تشغيل ingestion job بنجاح مع batches وlogs.
يمكن تحويل staging data إلى data mart بسيط.
يمكن حساب metric وKPI وتخزين snapshot.
يمكن تشغيل data quality rule وإظهار findings.
يمكن ربط field بقاموس بيانات ومالك بيانات.
يمكن dashboard أن يقرأ من snapshot بدل تشغيل query ثقيل.
يمكن export خارجي أن يعمل بصلاحيات محددة وسجل واضح.
AI report explainer لا يرى إلا البيانات المصرح بها والمخففة الحساسية.
كل jobs الثقيلة queued وتملك retry/error logs.
42. ما لا يدخل في البداية
Lakehouse كامل من أول إصدار.
Real-time streaming لكل الأحداث.
Self-service SQL مباشر للمستخدمين.
Machine Learning platform كامل.
Multi-tenant cross-customer benchmarking بدون موافقات صريحة.
نسخ كل البيانات الحساسة إلى warehouse بلا تصنيف أو retention.
43. الخلاصة
Data Warehouse / Data Platform هي الطبقة التي تجعل Kabeeri Enterprise قابلًا للتحليل والقياس والحوكمة دون قتل قواعد التشغيل اليومية. يجب أن تبدأ صغيرة فوق Advanced Reporting، ثم تتوسع في V6 إلى marts وmetrics وKPIs وdata dictionary وdata quality وexternal BI exports.
القاعدة: لا dashboard ثقيل من operational tables، لا export بدون policy، لا AI analytics بدون minimization، ولا Data Platform بدون owner وlineage وquality rules.

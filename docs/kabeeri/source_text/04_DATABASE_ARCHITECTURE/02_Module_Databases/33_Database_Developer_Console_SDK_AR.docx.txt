KABEERI Database File 33
Developer Console & SDK Database
قاعدة بيانات منصة المطورين وواجهة الـ SDK — KABEERI
هذا الملف يصف تصميم قاعدة البيانات الخاصة بمنصة المطورين داخل KABEERI: حسابات المطورين، مشاريع SDK، مفاتيح API، sandboxes، CLI tokens، التوثيق، API Explorer، شهادات المطورين، وأدوات إرسال الحزم للمراجعة والنشر.
الملف لا يستبدل Internal Marketplace & Packages Database؛ بل يضيف طبقة Developer Console فوقه. مصدر الحقيقة للحزم والإصدارات والتوقيع والمبيعات يبقى في نظام Marketplace/Packages، أما هذا الملف فينظم تجربة المطور وأدواته وحساباته.
1. الهدف من Developer Console & SDK Database
تمكين المطورين والشركاء من بناء Plugins وThemes وModules وConnectors وAI Skills بطريقة منظمة.
منع تعديل Core مباشرة، وإجبار كل توسعة على استخدام Events وHooks وAPIs وExtension Points.
إدارة حسابات المطورين والتحقق والشهادات والصلاحيات وسجل النشاط.
إدارة SDK Projects وSandbox Instances وAPI Explorer وCLI Tokens.
ربط عملية إرسال الحزم للمراجعة بنظام Internal/Public Marketplace بدون تكرار جداول الحزم.
تجهيز V6 للـ Public Developer Marketplace وEnterprise Private Marketplace.
2. موقعه داخل معمارية KABEERI
Developer Console يجلس فوق Core Kernel وMarketplace/Packages وSecurity وIntegration Hub. لا يمتلك بيانات العملاء التشغيلية، ولا يفتح وصولًا مباشرًا لجداول حساسة؛ بل يمنح المطور أدوات بناء آمنة، مفاتيح scoped، وبيئات اختبار منفصلة.

-> API Tokens / Sensitive Logs / Package Security

4. المبادئ الحاكمة
No direct Core modification: المطور لا يعدل ملفات Core مباشرة.
Manifest first: أي Plugin/Theme/Module/Connector/AI Skill يجب أن يملك manifest واضح.
Permission disclosure: لا حزمة بدون إعلان صلاحيات وdata scopes.
Sandbox before production: كل تكامل أو SDK project يجب اختباره في بيئة sandbox.
Scoped API access: كل API token يجب أن يكون محدودًا بالـ scopes والبيئة.
Audit by default: كل action للمطور، خصوصًا submission/review/token، يسجل في audit.
Review/signing before public marketplace: لا نشر عام قبل review pipeline وpackage signing.
Enterprise private marketplace: الشركات الكبيرة يمكن أن تمتلك نطاق مطورين وحزم خاصة بها.

10. Developer Onboarding Flow
User enables Developer Console
-> developer_account created
-> developer_profile draft created
-> optional developer_organization created
-> accept developer terms
-> run onboarding checklist
-> create sdk_project
-> generate CLI token
-> create sandbox
-> validate starter manifest
-> run sdk_test_run
-> ready for package submission
11. Package Submission Flow
Developer creates SDK project
-> writes package manifest
-> package:validate command runs
-> permissions and data scopes parsed
-> compatibility matrix checked
-> sdk_test_runs created
-> developer_submission_session created
-> submit to Marketplace review pipeline
-> developer_submission_links points to package_submission
-> security review and signing happen in Packages system
-> result shown in Developer Console
12. API Explorer Flow
Developer opens API Explorer
-> selects sandbox environment
-> endpoint permission/scope displayed
-> token scope checked
-> request sent to sandbox/public test API
-> response logged in api_explorer_requests
-> sensitive fields masked
-> example can be saved to docs/snippet
13. Sandbox Rules
Sandbox لا يستخدم بيانات عملاء حقيقية إلا إذا كانت anonymized وبموافقة واضحة.
كل Sandbox له expiry لتقليل التكلفة.
كل Connector sandbox يجب أن يستخدم test credentials أو mock provider.
AI Skill sandbox يجب أن يعمل مع data masking وguardrails.
Sandbox destruction لا يجب أن يؤثر على package submission history.
14. Security Requirements
لا تحفظ API tokens أو CLI tokens أو webhook secrets كنص واضح.
كل tokens يجب أن تكون scoped ويمكن إلغاؤها.
كل package submission يجب أن يملك audit trail.
API Explorer يجب أن يخفي الحقول الحساسة من logs.
Developer webhooks يجب أن تستخدم HMAC أو secret hash.
Developer accounts المعلقة لا يمكنها إرسال packages أو إنشاء tokens جديدة.
Enterprise private marketplace يحتاج approval قبل التثبيت وversion pinning.

17. Portable / Dedicated / Enterprise Rules
الوضع
السلوك
Cloud
Developer Console مركزي داخل Kabeeri، ويرتبط بالحزم والسوق الرسمي.
Frontend Anywhere
لا يتغير Developer Console؛ الواجهة الخارجية لا تحصل على صلاحيات تطوير.
Portable
لا يتم تصدير Developer Console كاملًا؛ يتم تصدير installed packages وmanifests اللازمة للتشغيل.
Dedicated
يمكن أن تمتلك enterprise private developer console أو private marketplace مع sync محدود للمراجعات والتحديثات.
Enterprise
يدعم private publishers، version pinning، approvals، certifications، وsupport access مضبوط.

21. Acceptance Criteria
يمكن لمستخدم إنشاء Developer Account بدون إعطائه صلاحيات platform admin.
يمكن إنشاء SDK Project مع project_type واضح.
يمكن توليد CLI token وAPI token scoped بدون تخزين النص الواضح.
يمكن تشغيل package manifest validation قبل الإرسال.
يمكن إنشاء Sandbox واستخدام Seed آمن ثم إزالته.
يمكن تسجيل API Explorer requests مع إخفاء البيانات الحساسة.
يمكن إرسال Package Submission وربطه بمراجعة Marketplace بدون تكرار جداول الحزمة.
كل أفعال المطور الحساسة تظهر في developer_audit_logs أو audit_logs المركزي.
Public Developer Marketplace لا يفتح إلا بعد review/signing/certification.
22. أخطاء ممنوعة
لا تجعل Developer Console يصل مباشرة إلى بيانات العملاء.
لا تسمح بحزم بدون manifest أو permission disclosure.
لا تخزن secrets أو tokens plain text.
لا تجعل API Explorer يعمل على production data افتراضيًا.
لا تفتح Public Developer Marketplace قبل review/signing كامل.
لا تخلط Developer account مع Organization customer account بدون ربط صريح.
لا تجعل sandbox بلا expiry أو بلا quotas.
لا تسمح بتثبيت enterprise private packages بدون approval/version pinning.
23. الخلاصة التنفيذية
Developer Console & SDK Database هي طبقة تمكين المطورين داخل KABEERI. هدفها جعل المنصة قابلة للتوسع مثل WordPress، لكن بطريقة محكومة وآمنة مثل منصة Enterprise. لذلك تفصل بين تجربة المطور وأدواته من جهة، وبين Marketplace/Packages كمصدر حقيقة للحزم والمراجعات والتوقيع من جهة أخرى.
القاعدة النهائية: Developer Console يعطي الأدوات والبيئات والتوثيق، Marketplace يعطي النشر والتوزيع والحوكمة، Security يعطي الحدود والتدقيق، وCore يحافظ على الهوية والصلاحيات.

KABEERI Database File 08
Kabeeri Media & Files Database
نظام الميديا والملفات والمستندات
ملف تفصيلي لقاعدة بيانات Media Library وDocument Management Foundation داخل KABEERI، ليخدم CMS وRabet وVerification وCommerce وERP وCloud وFrontend Anywhere وPortable وDedicated.
KABEERI / Kabeeri / kabeeri — powered by ADMIT
1. تعريف النظام
نظام Media & Files هو طبقة مركزية لإدارة كل ملف يرفعه المستخدم أو يولده النظام أو يحتاج أن يظهر في الموقع أو يدخل في مستند رسمي. هذه الطبقة لا تعني الصور فقط، بل تشمل الصور، الفيديوهات، ملفات PDF، المستندات القانونية، المرفقات، ملفات المنتجات، ملفات العقود، وملفات التصدير المؤقتة.
القاعدة الأساسية: لا نخزن الملفات نفسها داخل قاعدة البيانات. قاعدة البيانات تحفظ metadata، المسارات النسبية، الملكية، الصلاحيات، النسخ، والتحويلات. أما الملف الفعلي فيكون داخل storage disk مناسب.
2. علاقة هذا الملف بالملفات السابقة
الملف/النظام
كيف يعتمد على Media & Files
Core Kernel
يحتاج media_assets وmedia_usages كجزء من النواة، مع tenant scoping واضح.
CMS Database
يستخدم الصور المميزة، محتوى الصفحات، الميديا العامة، SEO images، وملفات القوالب.
Rabet / Verification
يستخدم المستندات القانونية، مستندات التحقق، نسخ المستندات، وسجلات الوصول الحساسة.
Commerce
يستخدم صور المنتجات، ملفات الكتالوج، ملفات الفواتير PDF، ومرفقات الطلبات.
ERP
يستخدم مستندات الموظفين، العقود، أوامر الشراء، الفواتير، ومرفقات المشاريع.
Cloud
يدير التخزين، الحصص، النسخ الاحتياطي، وملفات العملاء داخل Kabeeri Cloud.
Frontend Anywhere
يعطي الواجهة الخارجية حق قراءة public media فقط أو static snapshots.
Portable
يحتاج تجميع media/public وmedia/private وdocuments داخل export bundle.
Dedicated
يستخدم نفس schema، لكن storage/database قد تكون مخصصة للعميل.
3. الفرق بين Media Library وDocument Management Foundation
النوع
الوصف
أمثلة
Media Library
ملفات للاستخدام العام أو التحريري داخل الموقع/المتجر.
صور صفحات، صور مقالات، صور منتجات، ملفات تحميل عامة، فيديوهات.
Document Management
مستندات أعمال لها صلاحيات، نسخ، حالة، انتهاء، أرشفة، وأحياناً اعتماد أو توقيع.
مستندات قانونية، عقود، فواتير PDF، مستندات موظفين، مستندات تحقق، أدلة نزاعات.
مهم: يمكن أن يعتمد document_versions على media_assets، لكن document ليس مجرد media_asset. المستند له lifecycle وصلاحيات ومعنى قانوني أو تشغيلي.
4. مبادئ التصميم
كل ملف يجب أن يكون tenant-scoped عبر organization_id، وعند الحاجة site_id أو company_id.
كل ملف عام يجب أن يكون قابل للتخزين على CDN، وكل ملف خاص يجب أن يقدم عبر signed URL أو controller محمي.
كل وصول لملف sensitive يجب أن يسجل في media_access_logs أو document_access_logs.
كل ملف يجب أن يكون export-ready من اليوم الأول، باستخدام relative_path وليس URL كامل.
كل عملية معالجة ثقيلة مثل thumbnails أو virus scan أو metadata extraction يجب أن تعمل في queue.
لا نعتمد على visibility فقط للأمان؛ يجب وجود Policies وAccess Grants وScopes.
الأصل لا يتغير عند إنشاء thumbnails أو optimized versions؛ التحويلات تحفظ في media_derivatives.
5. Storage Modes
الوضع
الاستخدام
ملاحظات
local
التطوير وSelf-hosted البسيط.
جيد في V1، لكن يحتاج مسارات منظمة.
cloud_storage
Kabeeri Cloud managed storage.
يرتبط بالحصة والفوترة والنسخ الاحتياطي.
s3_compatible
Object storage عام أو خاص.
مناسب للتوسع وDedicated.
private_storage
مستندات حساسة.
يجب أن يقدم عبر signed URLs مع logging.
cdn_public
ميديا عامة عالية الزيارات.
لا يستخدم للملفات الخاصة.
6. هيكل المجلدات المقترح
يجب تجنب تخزين كل ملفات العملاء في مجلد واحد. الهيكل المقترح:
organizations/{organization_uuid}/sites/{site_uuid}/media/yyyy/mm/{file_uuid}.{ext}organizations/{organization_uuid}/companies/{company_uuid}/documents/yyyy/mm/{document_uuid}/{version_uuid}.{ext}organizations/{organization_uuid}/exports/{export_uuid}/bundle.ziporganizations/{organization_uuid}/temp/uploads/{upload_session_uuid}/chunk_{n}
استخدام UUID في المسار أفضل من id الداخلي لأنه يساعد في Portable وDedicated وExternal sync بدون كشف تسلسل قواعد البيانات.

28. Document Management Foundation
Document Management لا يحل محل Media Library، بل يبني عليها. المستند يمكن أن يحتوي على نسخة أو أكثر، وكل نسخة تشير إلى media_asset. المستند نفسه يحمل الحالة، النوع، الصلاحيات، الانتهاء، الأرشفة، والعلاقة بالكيان التشغيلي.

37. Upload Flow
User uploads file→ validate permission→ validate storage policy→ create media_upload_session→ store file or chunks→ create media_asset→ queue virus scan / metadata extraction / thumbnails→ create media_derivatives→ update processing_status = ready→ create media_usage if linked to object→ log activity
38. Private File Access Flow
User requests private file→ resolve media_asset→ check tenant scope→ check policy / role / media_access_grants→ if allowed create short-lived signed URL or stream through controller→ create media_access_log→ if denied create denied log for sensitive assets→ return file
39. Document Version Flow
User uploads new document version→ check document permission upload_version→ create media_asset→ create document_version version_number + 1→ mark previous version superseded if needed→ update documents.current_version_id→ create document_status_event→ create document_access_log→ notify reviewers if status requires review
40. Verification Document Flow
Company owner submits verification document→ create media_asset visibility=sensitive→ create document document_type=verification_document→ create document_version→ link document to verification_request→ create verification_documents row if module requires compatibility→ legal/internal reviewer sees assigned documents only→ every preview/download is logged
41. Frontend Anywhere Rules
الواجهة الخارجية تقرأ فقط media_assets ذات visibility = public أو مشتقات عامة مصرح بها.
لا تصل إلى private documents أو sensitive files أو verification documents.
يفضل تقديم public media عبر CDN أو public API scoped.
أي media في content snapshots يجب أن يكون public_url آمن ولا يكشف مسارات private storage.
عند تحديث media مستخدمة في صفحة منشورة يتم إطلاق frontend_cache_invalidations.
42. Portable Export Rules
media_assets العامة تخرج داخل media/public.
private files تخرج داخل media/private إذا كانت ضمن نطاق العميل ومسموح تصديرها.
documents تخرج داخل documents إذا طلب العميل وسمحت الخطة والسياسة.
export manifest يجب أن يحتوي checksums للملفات المهمة.
لا تصدر platform secrets أو ملفات تخص عملاء آخرين أو مستندات legal partner غير تابعة للعميل.
يجب الحفاظ على UUIDs وrelative_path قدر الإمكان لتسهيل restore وMall Sync.
43. Dedicated Rules
Dedicated يستخدم نفس الجداول داخل قاعدة العميل، لكن media_storage_disks قد تشير إلى storage مخصص.
Central Kabeeri لا يحتاج الوصول إلى الملفات الخاصة إلا عبر support access مؤقت وموافق عليه.
Health report يمكن أن يرسل إحصاءات فقط مثل storage_usage وfailed_jobs بدون بيانات حساسة.
Backups يجب أن تشمل database + files + document storage حسب سياسة العميل.
44. Security Requirements
File validation حسب mime type والحجم والامتداد.
منع تنفيذ الملفات المرفوعة ككود.
عدم استخدام original_filename كمسار تخزين مباشر.
استخدام signed URLs قصيرة المدة للملفات الخاصة.
تسجيل الوصول إلى sensitive files.
Virus scan foundation حتى لو بدأ كـ placeholder.
CORS وpublic API scopes للـ Frontend Anywhere.
عدم حفظ API keys أو tokens أو secrets كـ plain text في metadata.
45. Performance Requirements
Thumbnails وimage optimization في queues.
استخدام pagination في Media Library.
فهرسة organization_id وsite_id وcompany_id وasset_type وvisibility.
عدم تحميل metadata ضخمة بدون حاجة في القوائم.
استخدام CDN للميديا العامة عالية الزيارات.
تجميع usage counters بشكل دوري وليس في كل request إن أمكن.
تنظيف upload sessions المنتهية وderivatives غير المستخدمة عبر cleanup jobs.

51. الخلاصة
Media & Files Database ليست مجرد جدول صور. هي طبقة ثقة وأمان وتصدير وتشغيل. إذا صممت بشكل ضعيف ستتعطل مستندات التحقق، Portable export، Frontend Anywhere، Dedicated backups، وملفات ERP. لذلك يجب تثبيتها مبكراً مع Core Kernel وCMS، مع فصل واضح بين media العامة والمستندات الحساسة.

Media stores files. Documents govern business meaning. Access logs protect trust. Relative paths protect portability.

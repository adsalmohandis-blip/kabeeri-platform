1. تعريف Commerce Database
Commerce Database هي الطبقة التي تجعل Kabeeri قادرا على بيع المنتجات والخدمات واستقبال الطلبات بطريقة آمنة وقابلة للتوسع. في V2 تبدأ هذه الطبقة كـ Commerce Foundation بسيط، ثم في V3 تتحول إلى Commerce Pro V1 مرتبط بالمخزون والفواتير والضرائب والشحن، ثم في الإصدارات اللاحقة تتوسع إلى Multi-vendor وMall Commerce وERP-linked Commerce.
الهدف ليس بناء بديل كامل لـ Shopify من أول نسخة، بل بناء أساس متين لا يكسر لاحقا عند إضافة Inventory وInvoicing وAccounting وMall وIntegration Hub.
2. نطاق الملف
Catalog: المنتجات، التصنيفات، الصور، الأسعار، المتغيرات، والـ SKU.
Cart & Checkout: السلة، عناصر السلة، جلسات الدفع، وإعادة حساب الإجماليات من السيرفر.
Orders: الطلبات، عناصر الطلب، العناوين، تاريخ الحالات، وربط الطلب بالفاتورة والمخزون.
Customers: العملاء، العناوين، قنوات التواصل، وربطهم بالطلبات والـ CRM لاحقا.
Coupons & Discounts: كوبونات V2، ثم قواعد خصم أوسع في V3.
Payments: طرق دفع أساسية، معاملات دفع، Manual/COD/Bank Transfer كبداية، ثم بوابات دفع لاحقا.
Shipping & Taxes: foundation للشحن والضرائب، مع Country Packs لاحقا.
Integration: الربط مع Inventory، Invoicing، Mall Mirror، Frontend Anywhere، Portable، Dedicated.

4. مبادئ تصميم Commerce
لا نثق في أسعار السلة القادمة من الواجهة. كل subtotal وtax وdiscount وtotal يعاد حسابه server-side.
كل جدول أساسي يجب أن يكون scoped بـ organization_id، ومعه site_id أو company_id عند الحاجة.
المنتج قد يظهر في Site، وقد يرتبط بـ Company أو Business Profile، وقد يظهر لاحقا في Mall Mirror.
لا نحذف طلبا مؤكدا أو حركة دفع أو حركة مخزون بدون audit trail. نستخدم status/cancellation/refund بدلا من الحذف.
نفصل بين فواتير منصة Kabeeri للعميل وبين فواتير العميل لعملائه. invoices_platform شيء، customer_invoices شيء آخر.
Payment provider data تحفظ كـ metadata محدودة وآمنة، ولا تخزن card numbers أو payment tokens حساسة إلا عبر vault/provider.
Commerce V2 يجب أن يعمل حتى بدون ERP كامل. لكن تصميمه يترك hooks واضحة لـ Inventory وInvoicing وAccounting.

44. Product Publishing Flow
Create product draft→ upload product media→ set category / price / SKU→ validate required fields→ publish product→ create activity log→ optional: update sitemap/search index→ optional: sync public product to Mall Mirror if consent exists
45. Cart & Checkout Flow
Visitor adds product to cart→ cart_item created with snapshot→ cart totals are estimated→ checkout_session created→ server recalculates product prices, discounts, tax, shipping→ validate stock availability→ create order + order_items→ create payment_transaction or manual payment instruction→ cart status converted→ OrderCreated event fired
46. Payment Flow في V2
Order created→ payment_status = unpaid→ selected method: COD / bank transfer / manual→ admin records payment manually or customer follows instructions→ payment_transaction created→ order.payment_status updated→ OrderPaid event fired if paid→ optional invoice generation in V3
في V2 لا يجب تخزين أي بيانات دفع حساسة. بوابات الدفع الكاملة تدخل تدريجيا عبر Commerce Apps أو Integration Hub، مع إعلان الصلاحيات المطلوبة لكل مزود دفع.
47. Inventory Link Flow في V3
Order confirmed→ check commerce_inventory_links→ reserve stock in Inventory module if enabled→ create stock_reservation / stock_movement→ update order fulfillment_status→ low stock alerts may fire→ fulfillment/shipment updates inventory state
48. Order to Invoice Flow في V3
Order confirmed or paid→ create customer invoice draft/issued according to settings→ commerce_invoice_links created→ invoice PDF generated→ payment allocation optional→ accounting starter receives draft/posting event later
49. Frontend Anywhere Rules
الواجهة الخارجية تقرأ published products وpublic categories وpublic media فقط.
لا ترى cost_price أو stock internal details أو supplier data أو private customer data.
checkout headless يحتاج API key scopes: read_public_products, create_cart, create_order.
يجب تسجيل public_api_requests للطلبات العامة والتحكم في rate limits وCORS.
في المرحلة الأولى الأفضل: Catalog + Forms + Service Requests، ثم cart/order API لاحقا.
50. Portable Rules
products, categories, customers, orders, coupons يمكن تصديرها ضمن tenant export registry إذا كانت ضمن نطاق العميل.
payment tokens أو بيانات مزود دفع حساسة لا تصدر.
provider references قد تصدر فقط إذا كانت آمنة ومفيدة للمراجعة.
UUIDs يجب الحفاظ عليها لمزامنة Mall Mirror بعد الخروج.
ملفات media الخاصة بالمنتجات تدخل في media/public أو media/private حسب visibility.
51. Dedicated Rules
Dedicated يستخدم نفس Commerce schema داخل Dedicated DB لتوحيد الكود.
billing relationship يبقى في Kabeeri Central، أما orders/customers الخاصة بالعميل فتكون في Dedicated DB.
Mall Sync يتم عبر API/bridge وليس عبر قراءة Dedicated DB مباشرة.
health reports أو usage summaries لا يجب أن تحتوي بيانات عملاء أو تفاصيل طلبات حساسة.
52. Mall Sync Rules للمنتجات
Kabeeri Mall لا يعتمد مباشرة على جدول products. المنتجات العامة تنتقل إلى mall_mirror_products عبر mall_sync_sources وmall_sync_events بعد وجود موافقة نشر واضحة.

61. أخطاء ممنوعة
لا تحفظ card numbers أو CVV أو payment tokens داخل قاعدة بيانات Kabeeri.
لا تعتمد على السعر القادم من frontend.
لا تجعل stock_quantity داخل products هو مصدر الحقيقة بعد تفعيل Inventory module.
لا تخلط invoices_platform الخاصة بفوترة Kabeeri مع invoices الخاصة بعملاء المتجر.
لا تنشر المنتجات في Mall بدون consent وmoderation readiness.
لا تحذف orders أو payment_transactions بعد تأكيدها بدون audit/void/refund flow.
لا تبدأ بـ multi-vendor checkout قبل استقرار single-vendor commerce.
62. AI Build Prompts مقترحة
هذه prompts تستخدم عند بناء الموديول بمساعدة AI مع مراجعة بشرية:
ابن Laravel migration + model + policy لجدول products حسب Kabeeri Commerce Database، مع tenant scoping بـ organization_id وsite_id واختبارات صلاحيات publish/edit.ابن CartService يعيد حساب cart totals من قاعدة البيانات ولا يثق في السعر القادم من الواجهة، مع tests لإضافة منتج وتحديث كمية وحذف item.ابن OrderService يحول checkout_session إلى order/order_items ويولد order_number داخل organization، ويكتب order_status_history وactivity_log.ابن PaymentTransaction model وManualPaymentRecordAction بدون تخزين أي بيانات دفع حساسة، مع permission commerce.payment.record.ابن CouponService يدعم fixed_amount وpercentage وusage_limit ويكتب coupon_redemptions.
63. ملخص تنفيذي
هذا الملف يجعل Commerce في Kabeeri يبدأ صغيرا وآمنا في V2: products, cart, checkout, orders, customers, coupons, manual payments. ثم يترك مسارات واضحة للتوسع في V3: product variants, inventory link, invoice link, shipping/tax foundations, discount rules. كما يضمن أن Frontend Anywhere وPortable وDedicated وMall Sync لا تكسر ملكية البيانات أو خصوصية العميل.
القاعدة النهائية: Commerce لا يبقى متجرا منفصلا عن المنصة؛ بل يصبح جزءا من رحلة Build → Sell → Operate → Verify → Discover → Scale.
64. ملاحظات مرجعية داخلية
V2 يحدد Commerce Foundation: Products, Cart, Checkout basic, Orders, Customers, Coupons, COD/Bank Transfer.
V3 يضيف الربط التشغيلي: Inventory Basic, Invoicing Basic, Accounting Starter, Product variants, Shipping zones, Tax rules, Payment gateways initial.
Dependencies Map يضع Commerce Layer بعد Core/CMS وقبل ERP/Mall الكامل، ويؤكد اعتماده على Organizations, Sites, Companies optional, Business Profiles optional, Media, Content/SEO, Notifications, Activity Log.
Frontend Anywhere يسمح للواجهة الخارجية بقراءة المنتجات العامة وإنشاء cart/order فقط عبر scopes محددة.
Migration Strategy يضيف ضرورة دعم WooCommerce/Shopify mapping لاحقا بعد استقرار products/orders/customers/variants.

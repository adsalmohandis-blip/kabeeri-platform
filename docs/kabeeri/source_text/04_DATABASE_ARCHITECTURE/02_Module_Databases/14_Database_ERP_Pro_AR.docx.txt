KABEERI Database File 14 — Kabeeri ERP Pro Database
نظام ERP Pro + Advanced Operations + Commission + POS + Helpdesk + Contracts
هذا الملف يصف تصميم قاعدة البيانات الخاص بمرحلة ERP Pro في Kabeeri، وهي المرحلة التي توسع ERP Essentials إلى نظام تشغيل أعمق للشركات النامية، مع دعم العقود، الدعم الفني، نقاط البيع، العمولات، المدفوعات للشركاء، التقارير المتقدمة، والربط المنضبط مع Integration Hub.
ملاحظة مهمة: هذا الملف لا يستبدل ملف ERP Essentials، بل يبني فوقه. أي جدول موجود في Essentials يظل هو المصدر الأساسي، بينما يضيف ERP Pro جداول تفصيلية أو طبقات أعمق حوله.
1. الهدف من ERP Pro Database
الهدف هو تحويل Kabeeri من أساس تشغيل للشركات الصغيرة إلى طبقة ERP Pro قابلة للاستخدام من شركات نامية لديها عمليات مبيعات ومخزون ومشتريات ومحاسبة ودعم وعقود ونقاط بيع وعلاقات شركاء أكثر تعقيدًا.
توسيع CRM Lite إلى CRM Pro مع pipelines متعددة، activities، segmentation، وlead scoring.
توسيع Sales Basic إلى Sales Pro مع price lists، discount rules، sales orders، credit limits، وapproval thresholds.
توسيع Inventory Basic إلى Inventory Pro مع transfers، lots/serials، valuation، counts، reorder rules، وapproval controls.
توسيع Purchasing Basic إلى Requisitions، RFQs، supplier quotations، goods receipts، supplier bills، وsupplier performance.
إضافة Accounting Pro Foundation بدون الوصول بعد إلى Enterprise finance الكامل.
إضافة Contracts / CLM Foundation، Helpdesk / ITSM Foundation، POS Basic، Commission Engine، وPartner Payouts.
تجهيز جداول التوافق مع Integration Hub بدون خلط جداول الـ connectors داخل ERP نفسه.
2. موقع ERP Pro داخل خريطة Kabeeri
ERP Pro يعتمد على استقرار Core Kernel، Organizations، Companies، Users، Permissions، Activity/Audit Logs، Billing/Entitlements، Commerce Foundation، ERP Essentials، Workflows/Approvals، وIntegration Hub foundation.

4. مبادئ تصميم ERP Pro Database
كل الجداول التشغيلية يجب أن تكون scoped بـ organization_id، ومعظمها company_id.
لا يتم حفظ أسرار التكامل داخل ERP Pro؛ أي credentials تكون في Vault/Integration Hub عبر reference فقط.
أي عملية مالية أو مخزنية مؤثرة يجب أن تكتب في audit_logs أو domain-specific logs.
الـ UUID إلزامي للكيانات التي قد تنتقل بين Cloud / Portable / Dedicated أو تظهر في Integration mappings.
الجداول التي تولد قيودًا مالية أو مخزنية لا يتم حذفها فعليًا إلا وفق سياسات retention؛ الأفضل soft delete أو status.
أي اعتماد على Mall أو Rabet أو External Connector يجب أن يتم عبر reference أو sync event وليس علاقة DB مباشرة مع مصدر خارجي.
الفواتير التجارية للعميل لا تختلط مع invoices_platform الخاصة بفوترة Kabeeri نفسها.
Accounting Pro هنا foundation؛ لا نفتح enterprise accounting كامل قبل V6.

21. Flows تشغيلية أساسية
21.1 Sales Order Flow
Lead أو Deal ينضج داخل CRM Pipeline.
Quotation يتم إنشاؤه في Essentials أو Sales module.
عند قبول العرض يتم إنشاء sales_order.
إذا تخطى الخصم أو الإجمالي threshold يتم إنشاء approval_request.
بعد الاعتماد يتم تأكيد sales_order.
يتم حجز المخزون أو إنشاء stock movement حسب availability.
يمكن تحويل sales_order إلى invoice أو ربطه بـ customer invoice.
كل خطوة مهمة تسجل في activity_logs وaudit_logs عند الحاجة.
21.2 Purchase Requisition to Supplier Bill Flow
Employee ينشئ purchase_requisition.
Approval policy تحدد مسار الموافقة.
بعد الموافقة يمكن إنشاء RFQ أو PO.
Supplier quotation يتم تسجيله واختيار العرض المقبول.
Goods receipt يسجل الاستلام ويولد stock movements.
Supplier bill يسجل AP ويصبح قابلًا للترحيل المحاسبي.
Payment allocation يربط المدفوعات بفواتير المورد.
21.3 POS Basic Flow
Cashier يفتح pos_session على register محدد.
يضيف المنتجات إلى pos_order.
النظام يخصم المخزون عند الدفع أو الإغلاق حسب الإعداد.
pos_payment يسجل الكاش أو طريقة الدفع.
pos_receipt يصدر PDF أو رقم إيصال.
عند إغلاق الجلسة يتم إنشاء ملخص نقدي وقد يتم إنشاء journal draft.
21.4 Commission and Payout Flow
حدث تجاري يحصل: booking، package sale، legal review، reseller subscription.
commission_event يسجل الحدث وقيمته.
CommissionService يبحث عن commission_rule المناسب.
commission_calculation تنشأ بحالة pending أو approved.
بعد فترة hold تصبح payable.
payout_batch يجمع المستحقات.
payout_items تسجل المدفوعات للشركاء وتحدث الحالة.

24. Audit Requirements
تغيير حدود ائتمان العميل يجب أن يسجل audit_logs قبل/بعد.
تأكيد sales_order كبير أو خصم حساس يجب أن يسجل approval + audit.
تسويات مخزون أو stock counts approved يجب أن تسجل قبل/بعد.
ترحيل supplier bill أو journal posting rule يجب أن يسجل audit.
فتح أو إغلاق POS session يجب أن يسجل activity، وأي cash adjustment يسجل audit.
تغيير commission rule أو payout release يجب أن يسجل audit عالي المخاطر.
الاطلاع على contract documents الحساسة يجب أن يسجل sensitive access log إذا كانت مصنفة restricted.
25. Data Ownership Modes
الوضع
قواعد ERP Pro
Kabeeri Cloud
كل الجداول داخل Cloud DB مع tenant scoping. Backups وusage records داخل Cloud.
Frontend Anywhere
لا تتغير قاعدة ERP. الواجهة الخارجية لا تصل إلى ERP private data. يمكن فقط catalog/forms/orders public حسب scopes.
Kabeeri Portable
يجب تسجيل جداول ERP Pro داخل Tenant Export Registry. يتم تصدير بيانات الشركة التشغيلية حسب الخطة والموافقة.
Kabeeri Dedicated
نفس schema داخل Dedicated DB. Central Kabeeri يحتفظ فقط بعلاقة billing/license/sync/health، وليس تفاصيل ERP الخاصة.
Mall Sync
لا يرسل ERP Pro بيانات مالية أو مخزنية خاصة إلى Mall. يرسل فقط public products/services/status إذا كان هناك consent.

27. Performance and Indexing Notes
كل الجداول التشغيلية يجب أن تفهرس organization_id + company_id + status.
جداول sales_orders وsupport_tickets وcontracts تحتاج unique(company_id, number).
crm_deals تحتاج index(stage_id), index(owner_user_id), index(expected_close_date).
Inventory tables تحتاج فهارس product_id, warehouse_id, lot_id, serial_number.
Financial snapshots يمكن أن تكون derived/rebuildable لتخفيف الحساب المباشر.
report_exports وscheduled_report_jobs يجب أن تعمل عبر queue jobs.
public dashboards لا تقرأ مباشرة من جداول مالية كبيرة؛ تستخدم aggregates أو snapshots.
جداول audit والlogs لا تستخدم في UI اليومية إلا بفلاتر وتواريخ واضحة.
28. Migration from ERP Essentials to ERP Pro
تفعيل feature flags الخاصة بـ ERP Pro لكل شركة أو plan.
إنشاء default crm_pipeline وdefault stages من بيانات leads الحالية.
ربط quotations الحالية بـ sales_orders فقط عند الحاجة، وليس migration إلزامي.
تحويل warehouses الأساسية لتدعم transfers وcounts بدون تغيير identifiers.
ربط suppliers وpurchase_orders الحالية بدورة requisition/RFQ اختياريًا.
إنشاء chart/accounting rules بشكل draft حتى يراجعها finance user.
إنشاء approval_policies افتراضية منخفضة المخاطر وتعطيل الحساسة حتى يراجعها admin.
عدم تفعيل POS أو Commission Engine تلقائيًا إلا عبر entitlement.

30. Acceptance Criteria
يمكن إنشاء أكثر من sales pipeline وإضافة deals وتحريكها بين stages.
يمكن إنشاء sales order وربطه بquotation أو commerce order، ثم اعتماده حسب threshold.
يمكن تنفيذ stock transfer بين مخزنين مع تسجيل حركات واضحة.
يمكن تنفيذ stock count وتحويل الفروقات إلى adjustment بعد موافقة.
يمكن إنشاء purchase requisition ثم RFQ ثم supplier quotation ثم goods receipt ثم supplier bill.
يمكن تسجيل bank/cash accounts وتخصيص مدفوعات على AR/AP.
يمكن إنشاء contract مع parties/documents/renewal reminders وربطه بعميل أو مورد.
يمكن إنشاء support ticket مع SLA وتعيين وتعليقات وسجل حالة.
يمكن فتح POS session وإنشاء POS order ودفع نقدي وإغلاق الجلسة.
يمكن حساب commission من حدث تجاري ثم إدخاله في payout batch.
كل العمليات الحساسة لديها permissions واختبارات Policy واضحة.
كل جداول ERP Pro مدرجة في export registry أو معلن أنها لا تُصدر.

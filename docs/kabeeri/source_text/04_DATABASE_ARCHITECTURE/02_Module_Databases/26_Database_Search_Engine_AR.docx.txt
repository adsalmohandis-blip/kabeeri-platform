1. تعريف Search Engine داخل Kabeeri
Search Engine هو طبقة تشغيل مركزية تجعل البحث موحدا عبر CMS وMall وTalent وERP وDocuments وPackages، مع احترام الصلاحيات والخصوصية والسياق الحالي للمستخدم.
الهدف ليس بناء محرك بحث منفصل من اليوم الأول، بل بناء Database Foundation تسمح بالبدء بـ MySQL Search ثم الانتقال لاحقا إلى Meilisearch أو Typesense أو OpenSearch/Elasticsearch بدون إعادة تصميم جذرية.
• في V1: بحث إداري بسيط داخل Dashboard وSearchable interface/trait.
• في V2/V3: بحث أفضل للـ CMS والمنتجات وBusiness Directory والخدمات والمواهب.
• في V4/V5: بحث Mall وTalent وERP مع indexing jobs وranking signals.
• في V6: Enterprise Search يدعم dedicated clusters وadvanced analytics وdocument search.
2. لماذا نحتاج Database خاصة بالبحث؟
• Kabeeri ليست موقعا واحدا، بل منصة بها آلاف المواقع والشركات والمحتوى والمنتجات والطلبات والوثائق والـ ERP data.
• كل موديول لا يجب أن يبني بحثه الخاص بمعزل عن الباقي.
• البحث العام في Mall يختلف عن البحث الإداري داخل Organization ويختلف عن ERP Search.
• نتائج البحث يجب أن تكون permission-aware وvisibility-aware وtenant-scoped.
• الـ Search Index مشتق من البيانات الأصلية، ويجب أن يمكن إعادة بنائه في أي وقت.
• البيانات الحساسة مثل payroll وprivate documents وverification documents لا تظهر في search public indexes.
3. القاعدة الكبرى
Search Index ليس مصدر الحقيقة.
مصدر الحقيقة يبقى داخل جداول الموديولات الأصلية: CMS أو Commerce أو ERP أو Rabet أو Mall أو Documents. أما search_index_records فهو نسخة مشتقة للبحث فقط ويمكن حذفها وإعادة بنائها.
Source Table→ Domain Event→ Search Index Job→ search_index_records→ Search Provider Sync→ Permission-aware Query→ Results

5. مبادئ تصميم Search Database
• Tenant-scoped: أي record يحتوي organization_id عند الحاجة، ومعه company_id/site_id حسب السياق.
• Permission-aware: لا يكفي أن يكون السجل موجودا في index؛ يجب فحص صلاحيات المستخدم قبل عرضه.
• Visibility-aware: visibility وpublication_status وmoderation_status جزء من القرار.
• Rebuildable: أي index يمكن مسحه وإعادة بنائه من Source of Truth.
• Event-driven: تحديث الفهرس يتم عبر أحداث مثل ContentPublished وProductUpdated وCompanyVerified وMallListingPublished.
• Provider-agnostic: الجداول لا تفترض محرك بحث واحد فقط.
• No private leakage: لا تنسخ محتوى حساس إلى public search index.
• Soft-delete aware: السجلات المحذوفة أو المعلقة يجب أن تزال أو تخفى من نتائج البحث.

28. Permission-aware Search Flow
User submits query→ Resolve current context: platform / organization / company / site→ Load user memberships + roles + deny overrides→ Select allowed indexes→ Apply tenant filters→ Apply visibility filters→ Run search→ Post-filter sensitive results through AuthorizationService→ Log query→ Return results
29. Indexing Flow
ContentPublished / ProductUpdated / CompanyVerified / DocumentUploaded→ SearchIndexRequested event→ BuildSearchDocument action→ Sanitize sensitive fields→ Upsert search_index_records→ Upsert fields/facets/relations→ Sync to provider if enabled→ Mark indexed_at→ Emit SearchIndexUpdated
30. Reindex Flow
Admin starts reindex→ search_reindex_job created→ queue chunks by entity type→ each source record converted to search document→ failed items logged→ provider resync optional→ job completed→ health summary generated
31. Mall Search Flow
Mall Search لا يبحث في جداول العميل مباشرة. يبحث في Mall Mirror وMall Listings أو search_index_records المنشأة منها فقط.
Business/Profile/Product/Service approved for Mall→ Mall mirror updated→ MallListingPublished→ search_index_records upsert in mall_public index→ ranking signals calculated→ public search returns published + clean + consented results only
32. Document Search Flow
DocumentUploaded→ metadata extracted→ optional text extraction job→ sensitivity classification→ search_index_records created in documents_private→ permissions copied from document access policy→ search result requires document.view permission→ opening file creates sensitive access log if needed
33. Frontend Anywhere Rules
• Frontend Anywhere لا يحصل على admin search.
• يمكنه استخدام public search API فقط حسب scopes مثل read_public_content وread_public_products وread_public_services.
• الـ API key لا يسمح بقراءة drafts أو private documents أو ERP.
• Static Snapshot mode يمكن أن يولد search snapshot public فقط.
• أي query من الواجهة الخارجية يسجل في search_query_logs مع source = frontend_anywhere.
34. Portable Rules
• Portable يمكن أن يشغل search index محليا داخل self-hosted instance.
• عند Mall Sync، يرسل فقط public mirror data وليس operational/private data.
• UUIDs مهمة لمطابقة search records بين النسخة المحلية وMall Mirror.
• المنصة المركزية لا تعتمد على search المحلي لدى العميل؛ تعتمد على Mall Mirror المركزي.
35. Dedicated Rules
• Dedicated قد يستخدم search service منفصل حسب حجم العميل.
• يمكن الاحتفاظ بنفس schema داخل Dedicated DB لتوحيد الكود.
• Mall Search المركزي لا يقرأ Dedicated DB مباشرة، بل يتلقى sync عبر Mall Sync API.
• Enterprise clients يمكن أن يحتاجوا OpenSearch/Elasticsearch dedicated cluster لاحقا.

44. Data Sanitization Rules
• لا تفهرس passwords أو tokens أو secrets أو provider credentials.
• لا تفهرس private verification documents في public indexes.
• لا تفهرس supplier costs أو margins أو bank data أو payroll.
• لا تضع raw PII في public index إلا إذا كانت بيانات عامة بإذن صريح.
• في document search، يمكن فهرسة metadata فقط في البداية، ثم extracted text للمستندات المسموح بها.
• أي AI-generated search summary يجب أن يمر على privacy guardrails قبل الحفظ.

46. Testing Requirements
• User cannot see search result from another organization.
• Deny permission override hides result even if role allows it.
• Draft content does not appear in public site search.
• Suspended Mall listing does not appear even if source sends published.
• Private document appears only to authorized user and opening it logs access.
• Product update refreshes search index.
• Delete/Archive removes or hides search record.
• Reindex job can rebuild index from source tables.
• External provider sync failure is logged and retryable.
• Frontend Anywhere API cannot search admin/private records.
• Portable/Dedicated Mall search depends on Mall Mirror, not direct DB access.
• Query logs do not store sensitive payloads unnecessarily.
47. أخطاء ممنوعة
• لا تجعل search_index_records مصدر الحقيقة.
• لا تبحث في كل الجداول مباشرة بدون tenant scoping.
• لا تعرض نتائج قبل فحص visibility وpermissions.
• لا تضع بيانات payroll أو accounting أو legal private docs في public index.
• لا تعتمد على external search provider بدون fallback أو reindex plan.
• لا تخلط Mall public search مع Admin/ERP search.
• لا تسمح لـ Frontend Anywhere API key ببحث drafts أو private data.
• لا تنسى cache invalidation عند Content/Product/Profile updates.
• لا تحفظ search logs إلى الأبد بدون retention policy.
48. Build Order العملي

• 10. إضافة document search وsaved searches لاحقا.
49. Release Gate
• البحث الإداري يعرض فقط نتائج داخل سياق المستخدم.
• Public Site Search لا يعرض إلا published/public content.
• Mall Search يعمل بالتصنيف والدولة والمدينة والنوع بدون كشف بيانات خاصة.
• Reindex job يستطيع إعادة بناء الفهرس بالكامل.
• Search Index updates after publish/update/delete.
• Query performance مقبول مع pagination وفهارس مناسبة.
• Security tests تؤكد عدم تسريب بيانات بين tenants.
• Search logs لها retention policy أو pruning command.
50. الخلاصة التنفيذية
Search Engine Database هو طبقة تشغيل مركزية تجعل Kabeeri قابلة للاستخدام والاتساع. تبدأ بسيطة ببحث MySQL داخل V1/V2، لكنها تصمم من البداية كـ provider-agnostic, permission-aware, tenant-scoped, rebuildable search layer. نجاح هذه الطبقة يمنع تكرار منطق البحث داخل كل موديول، ويحمي من تسريب البيانات الحساسة، ويجهز Kabeeri لـ Mall وTalent وERP وEnterprise Search لاحقا.

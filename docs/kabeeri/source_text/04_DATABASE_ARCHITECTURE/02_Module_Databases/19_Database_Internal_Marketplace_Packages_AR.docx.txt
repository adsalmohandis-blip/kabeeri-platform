1. تعريف نظام Kabeeri Marketplace الداخلي
Kabeeri Marketplace هو السوق الداخلي داخل لوحة التحكم، وليس Kabeeri Mall العام. وظيفته توسيع المنصة عبر حزم رسمية أو معتمدة مثل البلجنز والثيمات والموديوالت والتكاملات وAI Skills، مع حوكمة تمنع فوضى إضافات WordPress وتمنع وصول الحزم لبيانات حساسة بدون تصريح.
في V4 يبدأ النظام كـ Internal Marketplace V1 بحزم رسمية فقط، ثم يتوسع في V5 إلى private packages وrevenue share، ثم في V6 إلى Public Developer Marketplace بعد اكتمال review/signing/certification.
2. لماذا يحتاج Marketplace Database مستقل؟
• لأن package ليس مجرد ملف كود؛ بل كيان له ناشر، إصدار، صلاحيات، اعتماديات، حالة مراجعة، توقيع، تنصيب، تحديث، وإزالة.
• لأن الحزمة قد تصل إلى بيانات حساسة مثل orders أو payments أو legal documents أو AI actions.
• لأن التثبيت يجب أن يمر عبر permission disclosure وcompatibility checks وsecurity review.
• لأن التحديث أو الإزالة قد يكسر الموقع أو يغير schema أو يحذف بيانات.
• لأن النظام سيحتاج لاحقًا revenue share وdeveloper payouts وprivate enterprise marketplace.

4. نطاق هذا الملف
4.1 يدخل في هذا الملف
• Package catalog الداخلي.
• Publishers وpublisher trust levels.
• Package manifests, versions, dependencies, compatibility.
• Package permissions وdata access scopes.
• Package signing وsecurity reviews.
• Review submissions وreview pipeline.
• Installations, activations, updates, uninstall records.
• Package events وactivity/audit logs.
• Ratings/reviews الداخلية للحزم.
• Revenue share وpayout foundation للأجيال القادمة.
• Private Marketplace للـ Enterprise لاحقًا.
4.2 لا يدخل في هذا الملف
• Kabeeri Mall العام الخاص بالشركات والخدمات والمنتجات والمواهب.
• Commerce orders/cart/checkout الخاصة بالعميل النهائي.
• Connector sync jobs التفصيلية؛ مكانها Integration Hub Database.
• AI prompt/plan/apply logs التفصيلية؛ مكانها AI Co-builder Database.
• ERP tables الخاصة بالمحاسبة والمخزون والمشتريات.

11. Install Flow
Open package page
→ Check feature flag / entitlement
→ Check package status = published
→ Check compatibility with Kabeeri/PHP/modules/country packs
→ Show permissions and data scopes
→ Risk classification
→ User confirms install
→ Queue install job if migrations/scans needed
→ Create package_installation
→ Store approved permission snapshot
→ Activate package
→ Fire PackageInstalled event
→ Create activity/audit log
12. Update Flow
New package version published
→ Compatibility check per installation
→ Security review status checked
→ Show changelog and new permissions
→ If new sensitive permissions: require approval
→ Create backup if package changes schema or code
→ Run update job
→ Update package_installations.package_version_id
→ Log package_update_logs
→ Fire PackageUpdated event
→ Rollback if failed and rollback_supported = true
13. Uninstall Flow
User requests uninstall
→ Show uninstall policy from manifest
→ Choose data_action
→ Require explicit confirmation if delete data
→ Optional export package data
→ Deactivate package
→ Remove settings or keep data based on policy
→ Create package_uninstall_record
→ Fire PackageUninstalled event
→ Audit log if sensitive data affected

15. Permission Disclosure Rules
• يجب عرض كل package_permissions وpackage_data_scopes قبل install أو update.
• إذا أضاف update صلاحيات جديدة، يجب طلب موافقة جديدة.
• الصلاحيات الحساسة مثل finance, payroll, legal documents, API secrets تتطلب review أعلى وربما workflow approval.
• الواجهة لا تكتفي باسم permission؛ يجب عرض سبب الحاجة والبيانات التي ستقرأها أو تكتبها الحزمة.
• لا يسمح بتثبيت package بصلاحية access_admin أو manage_permissions إلا في حالات رسمية محدودة وبـ audit logs.
16. Risk Levels
risk_level
المعنى
المتطلبات
low
قراءة بيانات عامة أو إعدادات بسيطة
permission disclosure فقط
medium
إنشاء/تعديل بيانات تشغيلية غير حساسة
موافقة admin + activity log
high
وصول إلى orders/payments/customers أو webhooks
security review + audit log
critical
finance/payroll/legal/API secrets أو تنفيذ كود عالي التأثير
manual review + workflow approval + restricted install
17. Security Rules
• ممنوع direct core modification.
• ممنوع hidden external calls غير معلنة في manifest.
• ممنوع stealing data أو bypassing permissions.
• ممنوع تعطيل audit logs أو sensitive access logs.
• ممنوع حفظ secrets داخل manifest أو settings غير مشفرة.
• أي package تستخدم webhooks أو external API يجب أن تعلن ذلك في manifest.
• أي package تحتاج finance/payroll/legal documents/API secrets تحتاج مراجعة صريحة.

الوضع

Frontend Anywhere
الحزمة تؤثر على backend/API داخل Cloud، وليس على الواجهة الخارجية إلا عبر snapshots/webhooks.
Portable
يجب تصدير installed packages وmanifest وversions وsettings ضمن portable bundle.
Dedicated
يمكن السماح بقنوات تحديث خاصة وprivate marketplace وupdate windows.
23. Portable Export Rules
• يجب تضمين installed_packages أو package_installations الخاصة بالعميل.
• يجب تضمين package manifests وactive versions وsettings.
• لا يتم تصدير global marketplace catalog بالكامل.
• لا يتم تصدير platform signing private keys أو review internal data.
• Portable instance يمكنها check updates عبر license/update channel إذا اختار العميل استمرار العلاقة.
24. Dedicated Rules
• Dedicated يمكن أن يمتلك private marketplace خاص بالعميل.
• التحديثات تمر عبر dedicated_update_windows.
• الحزم التي تحتاج support access يجب أن تسجل sensitive access logs.
• يمكن تفعيل version pinning لمنع التحديث التلقائي في بيئات Enterprise.
25. Billing & Revenue Share
في V4 يمكن أن تكون الحزم official/free فقط. في V5 يبدأ revenue share وprivate packages. في V6 يمكن فتح public developer marketplace مع subscriptions/certification/payouts.

29. Acceptance Criteria
• يمكن عرض package page داخل Dashboard.
• يمكن رؤية permissions وrisk level قبل install.
• لا يمكن تثبيت package غير published أو غير compatible.
• كل install/update/uninstall يسجل activity log.
• كل صلاحية حساسة تحتاج approval أو security review.
• يمكن إيقاف package أو تعليقها مركزيًا.
• يمكن تصدير package state مع Portable bundle بدون تسريب platform secrets.
• يمكن تشغيل official package install flow في V4 بدون فتح public marketplace.
30. أخطاء ممنوعة
• فتح Public Developer Marketplace قبل signing/review/permission display.
• السماح بحزم بدون manifest.
• السماح بحزم بدون صلاحيات معلنة.
• تثبيت حزم تصل للبيانات الحساسة بدون approval.
• عدم تسجيل install/update/uninstall في activity/audit logs.
• خلط Kabeeri Marketplace الداخلي مع Kabeeri Mall العام.
• إزالة package وحذف بياناتها بدون تأكيد صريح أو export option.
• تحديث package بإصدار جديد يكسر compatibility بدون تحذير أو rollback.
31. الخلاصة التنفيذية
Kabeeri Internal Marketplace هو العمود الفقري لتوسعة المنصة. لكنه لا يجب أن يبدأ كسوق عام مفتوح، بل كسوق داخلي رسمي ومتحكم فيه. قاعدة البيانات يجب أن تحفظ catalog وversions وmanifest وpermissions وreview/security/signing وinstall/update/uninstall state، حتى تكون Kabeeri قابلة للتوسعة مثل WordPress لكن محكومة وآمنة مثل Enterprise platform.

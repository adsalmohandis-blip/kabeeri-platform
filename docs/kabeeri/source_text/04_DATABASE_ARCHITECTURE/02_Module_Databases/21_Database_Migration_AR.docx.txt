1. تعريف Kabeeri Migration Database
Kabeeri Migration Database هي طبقة الجداول التي تسجل وتدير كل عمليات نقل البيانات من الأنظمة الخارجية إلى Kabeeri، سواء كانت الهجرة مرة واحدة أو مزامنة مرحلية أو import متكرر.
• تدير مصادر البيانات الخارجية مثل WordPress وWooCommerce وShopify وOdoo وZoho وQuickBooks وXero وDaftra وCSV/Excel.
• تسجل ملفات الاستيراد، mapping، التحويلات، أخطاء التحقق، preview، نتائج التنفيذ، redirects، وrollback.
• تدعم فكرة أن الهجرة ليست import فقط، بل دورة كاملة تبدأ بالتحليل وتنتهي بالمراقبة بعد Go Live.
• تمنع إدخال بيانات خطرة أو حساسة مثل payment tokens/cards.
• تربط كل سجل مستورد بالكيان الأصلي عبر external_id أو source_reference للحفاظ على idempotency ومنع التكرار.
2. أهداف النظام
1. تقليل خوف العملاء من الانتقال إلى Kabeeri.
2. الحفاظ على SEO عبر slugs وredirect maps وmetadata.
3. نقل المحتوى والوسائط والتصنيفات والمنتجات والعملاء والطلبات والمخزون والعملاء المحتملين.
4. توفير preview قبل تنفيذ import نهائي، خصوصا للمتاجر وERP.
5. توفير تقارير واضحة: ما تم استيراده، ما فشل، وما يحتاج مراجعة.
6. دعم rollback أو partial rollback قدر الإمكان.
7. دعم imports كبيرة عبر queue jobs قابلة للاستئناف.
8. تسجيل activity/audit/security logs للعمليات الحساسة.

4. مبادئ التصميم
• كل import يجب أن يكون scoped بـ organization_id، وعند الحاجة site_id وcompany_id.
• لا يتم import نهائي قبل validation وpreview، إلا في imports بسيطة ومنخفضة المخاطر.
• كل عملية import كبيرة يجب أن تعمل عبر queue job وتسجل progress وتدعم resume.
• أي import قد يغير بيانات إنتاجية مهمة يجب أن يسبقه backup أو rollback point.
• كل مصدر خارجي يجب أن يملك external identifiers لتجنب التكرار عند إعادة التشغيل.
• لا يتم خلط فواتير منصة Kabeeri مع فواتير العميل المستوردة.
• الـ mapping يجب أن يكون قابلا للحفظ وإعادة الاستخدام كـ template.
• لا يتم استيراد payment tokens أو card data أو secrets.

46. WordPress Migration Flow
1. إنشاء migration_project بنطاق site_id.
2. رفع WordPress XML في migration_uploaded_files.
3. تشغيل analyze job لاكتشاف pages/posts/authors/taxonomies/media/SEO.
4. إنشاء author/taxonomy/content/media maps.
5. تشغيل validation لاكتشاف slugs conflicts وmissing media وunknown shortcodes.
6. إنشاء preview_items للصفحات والمقالات والوسائط والـ redirects.
7. مراجعة التقرير والموافقة.
8. إنشاء rollback point أو backup قبل production import.
9. تنفيذ import على batches.
10. تفعيل redirect maps وتحديث sitemap.
11. تشغيل reconciliation وgo-live report.
47. WooCommerce Migration Flow
1. ربط WooCommerce API أو رفع export files.
2. تحليل products/variants/SKUs/customers/orders/coupons/reviews/shipping/tax.
3. إنشاء product maps وcustomer maps وorder maps وinventory maps.
4. مراجعة price/currency/tax/shipping mapping.
5. تشغيل preview مع إظهار المنتجات التي ستنشأ والطلبات التي ستستورد.
6. منع import لأي payment sensitive data.
7. استيراد المنتجات أولا، ثم العملاء، ثم الطلبات، ثم المخزون، ثم التقارير.
8. مطابقة source_count وtarget_count عبر reconciliation report.
48. Shopify Migration Flow
1. ربط Shopify API عبر Integration Hub أو رفع CSV exports.
2. تحليل products/collections/customers/orders/discounts.
3. mapping للـ variants والـ options والـ images.
4. تحويل collections إلى product categories أو taxonomies.
5. preview للمنتجات والطلبات والعملاء قبل import.
6. تسجيل external_links لمنع duplication عند delta imports.
7. تجهيز redirect maps من روابط Shopify القديمة إلى Kabeeri.
49. ERP / CRM Migration Flow
1. استخدام Connector من Integration Hub عندما يكون النظام مدعوما.
2. تحليل الحسابات والعملاء والموردين والفواتير والمدفوعات والمخزون والموظفين.
3. تجهيز finance/inventory/crm maps.
4. فرض approvals على أي import مالي أو محاسبي.
5. تشغيل dry run وreconciliation قبل production.
6. بدء sync مرحلي لو كان الاستبدال الكامل غير مناسب.

54. Security Rules
• لا يتم حفظ API keys أو passwords كنص واضح.
• لا يتم استيراد payment tokens أو card data أو secrets من أي نظام.
• أي import مالي أو ERP يجب أن يتطلب permission خاص وapproval وpreview.
• أي bulk import يجب أن يسجل audit event.
• أي import إلى production يجب أن يتحقق من entitlement ومن صحة operating mode.
• يجب تسجيل source file checksum وparser version لتتبع النتائج.
• يجب عزل ملفات الاستيراد الخاصة بالعميل داخل storage scope آمن.
• يجب وضع rate limits عند استخدام APIs خارجية.

58. Frontend Anywhere / Portable / Dedicated Considerations
• في Cloud وFrontend Anywhere مصدر البيانات داخل Kabeeri DB، لذلك import يعمل داخل المنصة مباشرة.
• في Portable قد يكون import داخل self-hosted installation، ثم يرسل Mall public data عبر sync فقط عند الموافقة.
• في Dedicated يتم تنفيذ import داخل Dedicated DB أو عبر managed migration window.
• عند الانتقال بين modes، يجب تسجيل tenant_transition وربط import/export بالـ business_passport.
• Mall Mirror لا يعتمد على source DB مباشرة، بل على public sync أو internal events بعد الموافقة.

61. Acceptance Criteria
• يمكن إنشاء migration_project وربطه بـ organization/site/company.
• يمكن رفع WordPress XML أو CSV وربطه بـ migration_uploaded_files.
• يمكن تشغيل analyze ثم validation ثم preview قبل import.
• يمكن حفظ mapping للكيانات والحقول والقيم.
• يمكن إنشاء redirect maps للروابط القديمة.
• يتم تسجيل external_links لكل سجل مستورد.
• يمكن إنشاء migration_report واضح للعميل.
• لا يتم استيراد بيانات دفع حساسة.
• تعمل rollback policy على الأقل للـ records التي تم إنشاؤها في import.
• كل العمليات المهمة تسجل activity/audit events.
62. أخطاء ممنوعة
• استيراد production بدون preview.
• تجاهل redirects أو slugs conflicts.
• إسقاط unknown shortcodes أو unsupported blocks بدون warning.
• حفظ API keys أو كلمات مرور المصدر كنص واضح.
• استيراد card data أو payment tokens.
• تشغيل import مالي بدون approval وreconciliation.
• عدم تسجيل external_id مما يسبب duplication عند إعادة التشغيل.
• خلط بيانات منصة Kabeeri المالية مع فواتير العميل المستوردة.
• تشغيل imports كبيرة داخل request عادي بدل queue job.
63. الخلاصة التنفيذية
Kabeeri Migration Database يجب أن تجعل الانتقال إلى Kabeeri منتجا موثوقا، وليس أداة import عشوائية. التصميم الصحيح هو Migration Center كامل يحلل البيانات، يرسم خرائطها، يتحقق منها، يعرض preview، يسمح بالإصلاح، ينفذ على دفعات، يحمي SEO، ويسجل كل شيء مع إمكانية rollback والمراقبة.
القاعدة النهائية:
No production migration without mapping, validation, preview, redirects, audit, and recovery path.

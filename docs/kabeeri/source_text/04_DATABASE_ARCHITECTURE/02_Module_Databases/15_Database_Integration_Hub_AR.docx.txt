KABEERI Database File 15 — Kabeeri Integration Hub Database
نظام Integration Hub + Connector Registry + Sync Engine + Webhooks
هذا الملف يصف تصميم قاعدة البيانات الخاص بـ Kabeeri Integration Hub، وهي الطبقة التي تربط Kabeeri بأنظمة خارجية مثل WordPress، WooCommerce، Shopify، Odoo، Zoho، QuickBooks، Xero، Daftra، Google Sheets/CSV، بوابات الدفع، مزودي الشحن، وأي نظام مخصص لاحقًا.
ملاحظة مهمة: Integration Hub لا يعني فتح وصول عشوائي لقواعد البيانات. كل اتصال يجب أن يكون عبر Connector معلن، صلاحيات واضحة، Credential Vault، Mapping Preview، Sync Logs، Retry Rules، وAudit.
1. هدف Integration Hub Database
الهدف من هذا النظام هو توفير طبقة ربط آمنة ومنظمة بين Kabeeri والأنظمة الخارجية، بحيث يستطيع العميل مزامنة البيانات أو استيرادها أو إرسالها بدون خلط المسؤوليات أو كشف الأسرار أو إفساد البيانات التشغيلية.
تسجيل connectors الرسمية والخاصة والمخصصة.
إدارة connections لكل Organization أو Company أو Site.
حفظ مراجع credentials بشكل آمن بدون تخزين plain text داخل الجداول العادية.
تعريف field mappings بين كيان Kabeeri والكيان الخارجي.
تشغيل sync jobs يدوية أو مجدولة أو event-driven.
تسجيل sync logs والأخطاء والمحاولات وإتاحة retry آمن.
استقبال webhooks من أنظمة خارجية والتحقق من التوقيع قبل المعالجة.
دعم preview / dry run قبل تطبيق تغييرات production.
ربط نتائج المزامنة بـ Activity Logs وAudit Logs وAI error explanation.
تجهيز Connector SDK V1 بدون فتح Public Developer Marketplace بالكامل.
2. موقع Integration Hub داخل Kabeeri
Integration Hub يبدأ في V5 فوق ERP Pro، لكنه يعتمد على Core وPermissions وAudit وBilling وWorkflows. لا يبدأ إذا كانت الصلاحيات أو الفواتير أو المخزون أو الأمان غير مستقرة.

4. مبادئ تصميم Integration Hub
No credential plain text: أي secret أو token أو password تحفظ كـ encrypted secret أو vault reference فقط.
Scope-first: كل connection لها scopes تحدد ماذا تقرأ وماذا تكتب.
Mapping before sync: لا يسمح لأي sync production بدون field mapping أو default mapping واضح.
Preview before apply: البيانات القادمة من نظام خارجي يجب أن تمر بـ dry run / preview للكيانات الحساسة.
Idempotency: أي webhook أو sync event يجب أن يمكن تكراره بدون إنشاء duplicated records.
Audit by default: أي sync يغير بيانات ERP أو Commerce أو Finance يسجل audit.
Error visibility: أخطاء المزامنة تظهر للمستخدم، ولا تختفي في logs داخلية فقط.
Retry with limits: retry rules محددة مع backoff وmax attempts، وليس loop مفتوح.
Disconnect safely: العميل يستطيع تعطيل connection بدون كسر البيانات المحلية.
No direct DB access: لا connector يقرأ/يكتب قاعدة Kabeeri مباشرة خارج Service/API contracts.
Tenant scoped: كل job أو mapping أو webhook مرتبط بـ organization_id، ومعه company_id/site_id عند الحاجة.
External IDs preserved: يجب حفظ external_id وexternal_system للمطابقة وحل التعارضات.

17. Sync Flow
أي sync حقيقي يجب أن يمر بالخطوات التالية:
التحقق من entitlement: هل الخطة تسمح بالـ connector؟
التحقق من permissions: هل المستخدم يملك صلاحية إنشاء/تشغيل sync؟
فحص connection health وcredential status.
تحميل entity mapping وfield mapping.
تشغيل preview أو dry run للكيانات الحساسة.
عرض summary/errors/conflicts للمستخدم عند الحاجة.
الحصول على approval إذا كان sync عالي المخاطر.
تشغيل apply mode عبر queue.
تسجيل sync_job_items لكل record.
إنشاء external_object_links أو تحديثها.
تسجيل Activity/Audit Logs وإشعار المسؤول.
فتح retry_queue أو sync_errors إذا فشل جزء من العملية.
Sync Flow:User/Admin starts sync→ EntitlementService check→ PermissionService check→ Connection health check→ Load mappings→ Dry run / preview→ Approval if high risk→ Queue sync job→ Process records idempotently→ Create/update external links→ Log activity/audit→ Notify owner→ Retry or conflict review if needed
18. Webhook Inbound Flow
استقبال request على webhook endpoint.
تحديد connection من endpoint_key أو headers.
التحقق من HMAC/OAuth/provider signature.
فحص idempotency عبر external_event_id أو payload_hash.
إنشاء incoming_webhook_event.
تحويله إلى sync_job أو domain event.
تسجيل log وnotification عند الفشل أو الحاجة لتدخل.

20. Security Requirements
لا تحفظ API keys أو OAuth tokens كـ plain text.
كل connector يعلن scopes قبل التفعيل.
أي وصول لـ finance أو payroll أو legal documents أو bank accounts يحتاج صلاحية صريحة.
كل webhook incoming يتحقق من signature.
كل outbound webhook يستخدم secret أو signature.
كل sync عالي المخاطر يحتاج preview وربما approval.
كل فشل authentication أو credential refresh يسجل security event.
rate limiting على public/inbound endpoints.
إلغاء connection يجب أن يوقف webhooks ويمنع jobs جديدة.
support diagnostics لا يرسل أسرار أو بيانات حساسة بدون consent.

27. Testing Checklist
اختبار أن Connector Registry يتحقق من manifest وrequired scopes.
اختبار أن Connection لا ينشأ بدون entitlement وpermission مناسبين.
اختبار أن Credentials لا تحفظ كنص واضح داخل قاعدة البيانات.
اختبار أن فشل OAuth token refresh ينشئ sync_error أو security event ظاهر.
اختبار أن Sync Preview يعرض أعداد create/update/skip/conflict.
اختبار أن High-risk sync لا يطبق بدون approval.
اختبار أن Webhook يرفض signature غير صحيح.
اختبار أن Duplicate webhook event يتم تجاهله بطريقة idempotent.
اختبار أن Retry Queue تحترم max attempts وbackoff.
اختبار أن غياب Mapping يمنع production sync.
اختبار أن مزامنة المخزون تنشئ stock movement ولا تعدل balance مباشرة.
اختبار أن Accounting sync يسجل audit events.
اختبار أن Disconnect يوقف jobs المستقبلية ويعطل webhook endpoints.
اختبار أن أوضاع Portable وDedicated تحفظ external_object_links عبر UUIDs.
اختبار أن Rate limits تمنع إساءة استخدام endpoints.
28. Portable / Dedicated / Frontend Anywhere Considerations
الوضع
قاعدة Integration Hub
Cloud
في وضع Cloud: كل connections وsync jobs داخل Cloud DB، والـ credentials تكون داخل vault مركزي أو encrypted storage.
Frontend Anywhere
في وضع Frontend Anywhere: الواجهة الخارجية لا تحصل على Integration credentials؛ أي form أو order يذهب إلى Kabeeri Public API ثم يعالجه Integration Hub داخليًا.
Portable
في وضع Portable: يمكن تصدير mappings وexternal links، لكن credentials تحتاج إعادة تسجيل أو portable vault منفصل. Mall Sync يستمر عبر self-hosted token منفصل.
Dedicated
في وضع Dedicated: يمكن تشغيل Integration Hub داخل Dedicated DB مع central registry محدود، أو hybrid حيث يبقى billing/license/connector catalog مركزيًا.
Mall Sync
في Mall Sync: لا يتصل Mall مباشرة بالتكاملات الخارجية؛ يعتمد على Mall Mirror أو Mall Sync API.

31. الخلاصة التنفيذية
Integration Hub هو طبقة خطرة ومهمة في Kabeeri V5. قيمته أنه يسمح للعميل بربط Kabeeri بأنظمته الحالية بدل إجباره على النقل الكامل فورًا. لكنه يجب أن يبنى بأمان شديد: scopes، vault، mapping preview، sync logs، retry، conflict resolution، audit، وفصل واضح بين connectors وبين جداول ERP/Commerce الأصلية.
القاعدة النهائية: No integration without scopes, no sync without mapping, no sensitive write without audit, no credential plain text, no dangerous apply without preview and approval.

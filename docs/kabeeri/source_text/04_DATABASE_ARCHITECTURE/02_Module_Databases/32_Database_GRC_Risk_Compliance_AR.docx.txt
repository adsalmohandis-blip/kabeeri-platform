KABEERI Database File 32
GRC / Risk / Compliance Database
قاعدة بيانات الحوكمة والمخاطر والامتثال — KABEERI
هذا الملف يصف تصميم قاعدة البيانات الخاص بطبقة GRC داخل Kabeeri، وهي طبقة Enterprise لا تبدأ قبل استقرار Core وRBAC وAudit وSecurity Center وERP Pro وIntegration Hub وBI Foundation.
الغرض من هذا الملف هو تحويل الحوكمة والامتثال من تقارير يدوية إلى نظام تشغيلي قابل للتتبع: سياسات، التزامات، مخاطر، ضوابط، اختبارات، أدلة، تدقيق داخلي، DOA، SoD، وخطط تصحيح.
1. هدف GRC Database
طبقة GRC تجعل المؤسسة قادرة على إدارة المخاطر والامتثال والسياسات والصلاحيات المؤسسية بطريقة قابلة للتدقيق، وليس فقط عبر ملفات خارجية أو جداول Excel.
توحيد السياسات وربطها بالموافقات والمراجعات الدورية.
تسجيل الالتزامات حسب الدولة أو اللائحة أو العقد أو المجال التشغيلي.
إدارة سجل مخاطر مركزي مع likelihood وimpact وmitigation وowner.
ربط الضوابط بالمخاطر والالتزامات والسياسات.
تشغيل اختبارات ضوابط دورية وتسجيل النتائج والأدلة.
إدارة خطط التدقيق الداخلي والنتائج والإجراءات التصحيحية.
تطبيق Delegation of Authority — DOA ومنع تضارب الصلاحيات — SoD.
إنتاج تقارير امتثال وتصديرات audit-ready بدون كشف بيانات غير مصرح بها.
2. موقع GRC داخل معمارية Kabeeri
GRC لا يستبدل Security أو BI أو ERP. هو طبقة حوكمة فوقهم: يأخذ إشارات من audit logs وsecurity events وERP approvals وbilling وcountry packs، ثم يحولها إلى obligations وrisks وcontrols وevidence وfindings.
النظام
دوره في GRC
Core Kernel
المصدر الأساسي للهوية، الشركات، المواقع، الصلاحيات، العضويات، activity/audit logs.
Security & Compliance
مصدر التصنيف، sensitive access، incidents، privacy requests، retention، SIEM exports.
ERP Pro
مصدر العمليات المالية والتعاقدية والمخزون والموافقات التي تخضع للضوابط.
BI / Analytics
يعرض مؤشرات المخاطر، اختبارات الضوابط، dashboard، compliance snapshots.
Country Packs
تحدد التزامات محلية مثل الضرائب، الفواتير الإلكترونية، payroll، data residency.
AI Co-builder
يمكنه اقتراح ضوابط أو تلخيص findings، لكنه لا يغير سياسات أو يغلق مخاطر بدون موافقة.
3. مبادئ التصميم
لا يوجد GRC بدون RBAC وAudit Logs؛ أي تغيير في سياسة أو خطر أو ضابط يجب تسجيله.
كل كيان GRC يجب أن يكون scoped بـ organization_id، وعند الحاجة company_id أو site_id.
السياسات والضوابط لها versioning؛ لا نعدل النسخ المعتمدة مباشرة.
الأدلة Evidence قد تكون ملفًا، رابطًا، لقطة تقرير، سجل Audit، أو نتيجة اختبار.
SoD وDOA قواعد قابلة للفحص آليًا، وليست ملاحظات نصية فقط.
GRC في V6 foundation وليس بديلًا كاملًا لمنصات GRC المتخصصة من اليوم الأول.
البيانات الحساسة داخل الأدلة يجب أن تستخدم Document/Media security وsensitive access logs.
كل تقارير GRC يجب أن تكون permission-aware وexport-logged.
4. الحدود بين GRC والأنظمة القريبة
المفهوم
مكانه الصحيح
ملاحظات

Core/Security

Incident Report
Security
قد ينشئ risk أو finding داخل GRC.
Approval Request
Workflow/ERP
DOA داخل GRC يحدد threshold والقواعد، والتنفيذ في Workflow.

GRC + ERP
تعريف الضابط داخل GRC، والبيانات التشغيلية داخل ERP.
Compliance Report
BI + GRC
GRC يحدد النطاق والأدلة، BI يعرض dashboards/snapshots.
Privacy Request
Security/Compliance
قد تربط كالتزام امتثال داخل GRC.
Country Regulation
Country Packs
تتحول إلى obligations داخل GRC حسب الدولة والقطاع.

42. Policy Lifecycle Flow
Create policy draft→ create policy version→ assign reviewers→ approvals collected→ version approved→ policy becomes active→ acknowledgements assigned→ review date scheduled→ evidence/report links generated→ audit log recorded
43. Obligation Lifecycle Flow
Country Pack / Regulation / Contract creates obligation→ owner assigned→ requirements defined→ evidence requirements defined→ controls linked→ due dates generated in compliance calendar→ evidence collected→ compliance status checked→ report snapshot created
44. Risk Register Flow
Risk identified from manual entry, incident, audit finding, AI suggestion, or failed control test→ risk category selected→ inherent likelihood/impact assessed→ controls mapped→ residual score calculated→ treatment plan created→ review date scheduled→ BI dashboard updated
45. Control Testing Flow
Control test due→ owner notified→ evidence collected→ test performed manually or by job→ result recorded→ if fail: finding/corrective action created→ risk reassessment triggered→ snapshot/dashboard updated
46. Internal Audit Flow
Audit plan created→ engagements defined→ scope items selected→ evidence requested→ fieldwork performed→ findings created→ corrective actions assigned→ verification evidence collected→ findings closed or risk accepted
47. DOA Flow
ERP/Workflow action requests approval→ DOA service checks subject type + amount + company + currency→ matching grc_doa_rule selected→ workflow approval steps generated→ decisions logged→ action allowed or blocked→ audit log created
48. SoD Detection Flow
Role or permission changes→ SoD detection job runs→ rules compare role/permission combinations→ conflict created if matched→ owner notified→ remove access / compensating control / accept risk / false positive→ resolution logged

52. تكامل GRC مع AI
AI يمكن أن يساعد في تلخيص مخاطر، اقتراح ضوابط، شرح findings، أو تجهيز policy draft. لكنه لا يعتمد سياسة، لا يقبل خطرًا، لا يغلق finding، ولا يمنح استثناء SoD بدون موافقة بشرية وصلاحية واضحة.
AI Action
الحد الأقصى المسموح
تلخيص policy أو finding
Read-only / low risk.
اقتراح risk treatment
Draft suggestion فقط.
إنشاء policy draft
Draft فقط، يحتاج approval.
إغلاق corrective action
ممنوع بدون evidence + approver.
قبول SoD conflict
ممنوع إلا workflow approval.

High-risk، approval مشدد + audit log.

54. Cloud / Frontend Anywhere / Portable / Dedicated
الوضع
قواعد GRC
Cloud
GRC tables داخل Cloud DB scoped by organization/company، مع exports وسجلات وصول.
Frontend Anywhere
لا يخرج GRC للواجهة العامة. يمكن عرض dashboards داخل Admin فقط.
Portable
يصدر GRC tenant data حسب الخطة والسياسات، لكن platform relationship records قد تبقى في Central.
Dedicated
GRC operational data داخل Dedicated DB، مع summaries أو compliance exports اختيارية للـ Central حسب العقد.
Mall Sync
لا يرسل GRC private evidence إلى Mall. يمكن إرسال trust/compliance badge public فقط بموافقة.

index على organization_id وcompany_id في كل الجداول الرئيسية.

61. أخطاء ممنوعة
لا تبني GRC قبل استقرار RBAC وAudit Logs.
لا تجعل risk register عامًا أو قابلًا للعرض في Mall.
لا تسمح بتعديل policy version المعتمدة مباشرة.
لا تحفظ evidence restricted بدون access logging.
لا تجعل AI يغلق findings أو يقبل risks بدون موافقة.
لا تخلط Compliance reports مع BI dashboards العامة بدون صلاحيات.
لا تجعل SoD مجرد تقرير؛ يجب أن ينتج conflicts قابلة للعلاج.
لا تجعل DOA نصًا حرًا فقط؛ يجب أن يتحول إلى قواعد قابلة للتنفيذ.
لا تصدر audit pack بدون export log وسبب وصلاحية.
62. الخلاصة التنفيذية
GRC في Kabeeri هو طبقة Enterprise تجعل الحوكمة جزءًا من التشغيل اليومي: السياسات مرتبطة بموافقات، الالتزامات مرتبطة بأدلة، المخاطر مرتبطة بضوابط، والضوابط مرتبطة باختبارات وتدقيق وإجراءات تصحيحية. بدون هذه الطبقة، تصبح Enterprise مجرد ميزات كثيرة بدون رقابة مؤسسية.

1. تعريف Onboarding Wizard
Onboarding Wizard هو نظام التهيئة الموجهة الذي يظهر للمستخدم بعد التسجيل أو عند بدء مساحة جديدة، ويساعده على اختيار المسار الصحيح ثم تنفيذ خطوات صغيرة قابلة للقياس حتى يصل إلى نتيجة عملية. الهدف ليس مجرد شاشة ترحيب، بل محرك إعدادات وتشغيل أولي قابل للتوسع مع كل موديول.
يسأل المستخدم عن هدفه الأساسي بدل عرض كل المنصة دفعة واحدة.
ينشئ Organization / Site / Business Profile / Store / Professional Profile حسب المسار.
يفعّل feature flags أو modules المسموحة حسب الخطة والصلاحيات.
يربط المستخدم بـ checklists وquick actions وrecommended next steps.
يسجل التقدم والأحداث والاختيارات حتى يمكن الرجوع والتحليل والتحسين.
2. لماذا يحتاج Onboarding إلى Database مستقلة؟
لأن Kabeeri منصة واسعة، ولا يكفي hardcoded setup wizard داخل الواجهة. نحتاج طبقة بيانات تعرف المسارات والنسخ والخطوات والإجابات والتوصيات والأفعال التي نفذها النظام. هذا يسمح بتغيير التجربة بدون إعادة نشر كود كبير، وبناء onboarding مختلف حسب الدولة والخطة ونوع العميل واللغة والموديولات المفعلة.
مستخدم يريد موقعًا بسيطًا يحتاج خطوات مختلفة عن مستخدم يريد متجرًا.
شركة تريد توثيق Rabet تحتاج مستندات ومسار تحقق.
وكالة تحتاج ربط عملاء ومواقع وصلاحيات.
Portable/Dedicated يحتاجان onboarding تقني مختلف عن Cloud.
AI-assisted onboarding في V6 يحتاج تخزين اقتراحات وخطط وسياق، وليس مجرد نصوص ثابتة.

4. مبادئ التصميم
المبدأ
الشرح
Context-first
المسار يتحدد حسب المستخدم والسياق: شخصي، منظمة، موقع، شركة، متجر، وكالة.
Permission-aware
لا تعرض خطوة لا يملك المستخدم صلاحيتها أو لا تسمح بها الخطة.
Feature-flag aware
كل خطوة يمكن ربطها بـ feature flag أو entitlement.
Progressive disclosure
لا تعرض كل قدرات Kabeeri في البداية.
Resumable
يمكن للمستخدم إيقاف المسار والرجوع لاحقًا.
Auditable
كل action مهم يسجل في Activity Log.
Portable-aware
التقدم والاختيارات يمكن تصديرها ضمن export package عند الحاجة.
Versioned flows
أي تعديل في flow لا يكسر sessions قديمة؛ لذلك نحتاج flow_versions.

31. Flow الظهور في Kabeeri Mall
لا يتم النشر في Mall بدون Consent وModeration readiness. Onboarding لا ينشر مباشرة؛ هو يجهز البيانات ويطلب الموافقة.
فحص وجود business profile public-ready.
فحص verification status أو trust badge إن وجد.
طلب mall_publication_consent.

39. Data Retention وPrivacy
إجابات onboarding ليست بديلًا عن بيانات الكيانات الرسمية؛ بعد إنشاء site أو company يصبح مصدر الحقيقة في جداولها الأصلية.
لا نخزن أسرار مثل API keys أو payment credentials داخل onboarding_answers.
يمكن حذف أو anonymize onboarding_events القديمة بعد مدة حسب privacy policy.
context snapshots يجب أن تكون مختصرة ولا تحتوي مستندات أو بيانات حساسة كاملة.
عند Portable export، يمكن تضمين onboarding_sessions/checklists كبيانات تشغيلية اختيارية، لكن platform analytics تبقى مركزية أو anonymized.

46. Acceptance Criteria
يمكن لمستخدم جديد إنشاء Organization وSite من wizard بدون دخول إعدادات معقدة.
يمكن حفظ التقدم والرجوع لاحقًا.
لا تظهر خطوات لا يملك المستخدم صلاحيتها.
أي Action مهم يسجل Activity Log.
كل flow قابل للتعطيل أو تغيير نسخه بدون كسر sessions القديمة.
توجد checklists عملية بعد إكمال المسار.
يمكن تتبع completion rate وdrop-off rate لاحقًا.
47. الخلاصة التنفيذية
Onboarding Wizard ليس شاشة ترحيب، بل طبقة تشغيل أساسية تمنع المستخدم من الضياع داخل منصة ضخمة. يبدأ في V1 بشكل بسيط لكنه يجب أن يبنى كقاعدة بيانات قابلة للتوسع، لأن كل موديول لاحق سيحتاج طريقة موجهة للدخول والاستخدام. القاعدة: لا تعرض كل Kabeeri مرة واحدة؛ اسأل المستخدم ماذا يريد، ثم أنشئ له المسار والبيانات والمهام المناسبة بأمان.

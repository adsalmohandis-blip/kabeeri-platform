Kabeeri CMS Database
نظام قاعدة بيانات إدارة المحتوى
هذا الملف يصف تصميم قاعدة البيانات الخاص بطبقة CMS داخل KABEERI، وهي أول طبقة منتج فوق Core Kernel، وتخدم المواقع، المدونات، الصفحات، المحتوى المنظم، القوائم، السيو، النشر، والربط مع Frontend Anywhere وPortable وDedicated.

1. هدف ملف CMS Database
تثبيت نموذج بيانات المحتوى قبل التوسع إلى Commerce وERP وMall.
توفير CMS قوي لكنه منظم، وليس نسخة من WordPress postmeta الفوضوية.
دعم Pages وPosts وContent Types وTaxonomies وRevisions وSEO من البداية.
ضمان أن المحتوى قابل للتصدير في Portable، وقابل للعرض عبر Frontend Anywhere، وقابل للعزل داخل Dedicated.
توفير أساس واضح للـ AI Co-builder لاحقًا بدون السماح بتعديلات مباشرة خطيرة على المحتوى المنشور.
2. موقع CMS داخل المعمارية العامة
يعتمد CMS على Core Kernel، ولا يملك هوية أو صلاحيات مستقلة. أي محتوى يجب أن يعرف: أي Organization؟ أي Site؟ أي Company عند الحاجة؟ من أنشأ؟ من نشر؟ وما حالة الظهور؟
Core Kernel→ Organizations→ Sites→ CMS Content→ Media references→ Theme rendering→ SEO / Sitemap→ Frontend Anywhere snapshots or APIs→ Portable export registry→ Dedicated tenant DB

4. مبادئ تصميم CMS
المبدأ
التفسير
Site-scoped
المحتوى يتبع Site داخل Organization، ولا يوجد محتوى عام عائم بدون مالك.
Typed Content
كل نوع محتوى له schema واضح بدل الاعتماد على metadata غير منضبط.
Revisionable
أي تعديل مهم على المحتوى يجب أن يترك revision يمكن الرجوع له.
Publishable
النشر له حالات واضحة: draft, review, scheduled, published, archived, trashed.
Portable
المحتوى قابل للتجميع والتصدير مع UUIDs وروابط media relative.
Frontend-ready
يدعم API وStatic Snapshots وCache invalidation للواجهات الخارجية.
SEO-ready
الـ slug وmeta وcanonical وredirects وsitemap ليست إضافات عشوائية.
Permission-aware
النشر والحذف وتعديل السيو وإدارة redirects صلاحيات منفصلة.

7. قاعدة Pages وPosts
في Kabeeri لا نحتاج جدول pages وجدول posts منفصلين في البداية. الأفضل أن يكون كلاهما content_entries بنوع محتوى مختلف:
content_types.slug = pagecontent_types.slug = postcontent_entries.content_type_id -> content_types.id
يمكن لاحقًا إضافة content types أخرى مثل: property, case_study, event, service_article، دون تغيير جذري في البنية.

31. Content Creation Flow
User opens Site Admin→ Permission check: content.create→ Select content_type→ Create content_entry as draft→ Fill base fields + custom field values→ Optional attach media→ Save revision→ Activity log created→ User previews content
32. Publishing Flow
Editor requests publish→ Permission check: content.publish→ Validate slug uniqueness→ Validate required fields→ Create revision snapshot→ status = published→ published_at set→ ContentPublished event fired→ Update sitemap_records→ Clear page cache→ Create frontend_cache_invalidations if Frontend Anywhere enabled→ Activity log + publication log
33. Slug Change Flow
Published content slug changes→ store old/new in content_slug_history→ suggest redirect→ if accepted: create redirects record→ update sitemap→ clear cache→ log activity
34. Menu Update Flow
Admin updates menu→ Permission check: menus.manage→ Validate item targets→ Save menu_items order→ MenuUpdated event fired→ ClearMenuCache listener→ Frontend webhook/cache invalidation if needed

41. Indexing & Performance Notes
كل queries العامة يجب أن تبدأ بـ site_id + status + visibility.
استخدم unique(site_id, slug) لتجنب تضارب الروابط.
لا تحمل revisions في شاشة قائمة المحتوى.
استخدم pagination في كل قوائم admin.
cms_search_index جدول مشتق ويمكن إعادة بنائه.
sitemap_records مشتق ولا يجب اعتباره مصدر حقيقة.
عند Frontend Anywhere، لا تضرب DB لكل طلب عام إذا كان Snapshot Mode مفعّلًا.
42. Security Rules
تنظيف HTML أو استخدام محرر موثوق يمنع XSS في public rendering.
عدم تنفيذ shortcodes أو scripts مستوردة من WordPress بدون sanitize.
التحقق من صلاحية content.publish منفصلة عن content.edit.
عدم عرض drafts أو revisions في Public API.
منع open redirects داخل redirects.
تسجيل حذف المحتوى المنشور أو rollback في audit_logs.
حماية form submissions بـ CSRF/rate limiting/spam checks.
عدم حفظ كلمات مرور visibility كنص صريح؛ استخدم password_hash.

49. Go / No-Go Criteria

يمكن إنشاء مقال وتصنيفه وعرض أرشيف المقالات.

Sitemap وRobots يعملان بشكل بسيط.
Revision ينشأ عند النشر ويمكن الرجوع له.
Menu يظهر في الثيم ويتحدث عند التعديل.
Redirects تعمل وتحمي URLs القديمة.
Frontend Anywhere لا يرى إلا محتوى public/published.
Portable export يستطيع تجميع جداول CMS بدون بيانات من عملاء آخرين.
اختبارات الصلاحيات الأساسية تمر.

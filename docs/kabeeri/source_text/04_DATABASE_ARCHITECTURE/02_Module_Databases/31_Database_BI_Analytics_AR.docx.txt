1. تعريف Advanced Reporting / BI / Analytics
نظام Advanced Reporting / BI / Analytics هو طبقة قراءة وتحليل فوق بيانات المنصة، وليس بديلاً عن جداول التشغيل الأصلية. هو لا يملك الحقيقة التشغيلية، بل يبني نماذج عرض وتحليل مشتقة من مصادر الحقيقة داخل الموديولات المختلفة.
في V5 يبدأ النظام كـ Advanced Reporting Foundation: تعريفات تقارير، فلاتر محفوظة، تقارير مجدولة، تصدير، وDashboard widgets.
في V6 يتوسع إلى BI / Analytics / Data Platform: Executive dashboards، Operational dashboards، KPI management، Data warehouse foundation، Data marts by domain، Data dictionary، Data quality، وScheduled analytics jobs.
أي تقرير يجب أن يكون tenant-scoped وpermission-aware وvisibility-aware.
التقارير الثقيلة لا تعمل داخل request مباشر، بل عبر queue jobs وsnapshots وcache.
2. أهداف النظام
إعطاء الإدارة رؤية تنفيذية على الشركات والمواقع والمتاجر والعمليات.
تحويل بيانات ERP وCommerce وRabet وMall إلى KPIs قابلة للمتابعة.
توفير Report Builder يمكن التحكم فيه بالصلاحيات بدون كشف بيانات حساسة.
دعم Scheduled Reports وتصدير PDF/Excel/CSV لاحقاً.
تأسيس Data Warehouse / Data Mart تدريجي بدون تعقيد مبكر.
دعم AI Report Explainer بدون السماح للذكاء الاصطناعي بتعديل البيانات التشغيلية.

4. القواعد الحاكمة
لا يوجد report يقرأ كل شيء بدون Scope واضح.
لا يمكن لتقرير أن يتجاوز صلاحيات المستخدم أو membership context.
البيانات الحساسة مثل payroll، bank accounts، legal documents، identity documents تحتاج permissions صريحة وaudit log.
أي dashboard عام يجب أن يستخدم public/aggregated data فقط.
الـ KPI نتيجة مشتقة، ويمكن إعادة حسابه من مصادر الحقيقة.
أي report ثقيل يجب أن يعمل queue/scheduled job وليس داخل HTTP request مباشر.
أي export يجب أن يسجل في activity/audit logs ويخضع لسياسة retention.

8. Report Builder Flow
Admin opens report builder→ choose dataset→ select allowed fields→ add filters/grouping/sorts→ permission check→ preview sample rows→ save report_definition→ run report_run→ cache or export if needed→ activity/audit log created
9. Dashboard Flow
Create dashboard_definition→ add widgets→ each widget uses report/kpi/dataset→ widget permission check→ run lightweight queries or cached snapshot→ dashboard_widget_data_snapshots updated→ user sees dashboard according to role/context
10. KPI Calculation Flow
Scheduled KPI job starts→ load kpi_definitions→ resolve organization/company scope→ read source dataset or data mart→ calculate value→ compare against kpi_targets→ store kpi_values→ notify if threshold warning/critical→ dashboard widgets refresh
11. Data Warehouse / Data Mart Flow
warehouse_job scheduled→ extract from source modules→ transform into domain mart→ aggregate metrics→ run data_quality_rules→ publish data_mart_tables→ mark stale dashboards for refresh
12. Security & Privacy Rules
كل report_run يجب أن يعرف organization_id وcontext المستخدم.
لا يسمح بتصدير بيانات حساسة إلا بصلاحية analytics.report.export_sensitive أو صلاحية domain محددة.
Payroll وbanking وlegal documents وidentity documents وsecurity events لا تظهر في BI العام.
Dashboard public لا يعرض إلا aggregated/anonymized data.
External BI export يحتاج approval وaudit log وexpiration/revocation.
Query builder لا يسمح بكتابة SQL خام من المستخدم النهائي في V5/V6 المبكر.
أي AI report explainer يقرأ summary آمن ولا يحصل على raw sensitive rows إلا بإذن صريح.

15. Frontend Anywhere / Portable / Dedicated
15.1 Frontend Anywhere
الواجهة الخارجية لا ترى تقارير admin أو raw analytics.
يمكن توفير public analytics محدودة مثل page views أو catalog stats إذا كان scope يسمح.
أي Dashboard إداري يبقى داخل Control Panel في Kabeeri Cloud.
15.2 Portable
عند تصدير العميل، يمكن تضمين report_definitions وdashboard_definitions وkpi_definitions الخاصة به.
لا تصدر platform-wide benchmark data أو بيانات عملاء آخرين.
يجب إعادة بناء snapshots وdata marts داخل النسخة self-hosted بعد restore.
15.3 Dedicated
Dedicated يمكنه تشغيل warehouse jobs داخل بيئة العميل.
Central Kabeeri يستقبل فقط usage summaries أو mall analytics العامة حسب الاتفاق.
يمكن تفعيل external BI exports بشكل منفصل لكل dedicated environment.
16. Indexing & Performance
استخدم snapshots للوحات التنفيذية المتكررة.
استخدم queued report_runs للتقارير الثقيلة.
استخدم data marts للـ joins الثقيلة بين ERP domains.
استخدم read replicas أو reporting database في المراحل المتقدمة.
احتفظ بـ query logs وduration_ms لتحديد التقارير البطيئة.
لا تسمح بتقارير مفتوحة بدون date range افتراضي.
17. AI Report Explainer
AI يشرح التقرير ولا يعدل التقرير أو البيانات الأصلية بدون approval.
AI يحصل على metadata وaggregated results قدر الإمكان بدلاً من raw rows.
أي تفسير AI يحفظ في ai tool calls أو analytics_ai_explanations إذا تم توسيع النظام.
يمكن ربط report_runs بـ ai_sessions عند طلب explanation.
AI Report Explainer FlowUser opens report→ permission check→ report summary generated→ sensitive fields removed or masked→ AI explains trend/anomaly→ explanation logged→ optional suggested actions require approval workflow

20. Definition of Done
يمكن إنشاء تقرير من Dataset آمن وتشغيله.
يمكن حفظ filters وviews.
يمكن تصدير تقرير بصلاحية واضحة وسجل audit.
Dashboard يعرض widgets من reports/KPIs.
KPI calculation job يعمل ويخزن values.
التقارير الثقيلة تعمل queue ولا تكسر request.
الـ permission-aware analytics يمنع رؤية بيانات غير مسموحة.
Data dictionary يشرح أهم المصطلحات والحقول.
Data quality rule واحدة على الأقل تعمل وتخزن result.
Portable/Dedicated لا يكسر report definitions بعد النقل.
21. ملخص تنفيذي
هذا الملف يحول التقارير من صفحات عشوائية داخل كل موديول إلى طبقة Analytics مركزية منظمة. البداية في V5 تكون Report Definitions وSaved Filters وScheduled Reports وDashboard Widgets. في V6 تتحول إلى BI/Data Platform يدعم KPIs وData Dictionary وData Quality وData Warehouse Foundation. القاعدة النهائية: التقارير تقرأ وتلخص وتشرح، لكنها لا تكسر صلاحيات النظام ولا تصبح مصدراً للحقيقة بدلاً من الموديولات الأصلية.

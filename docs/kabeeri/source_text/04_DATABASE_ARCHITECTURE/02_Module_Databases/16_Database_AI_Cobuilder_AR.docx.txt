KABEERI Database File 16
Kabeeri AI Co-builder Database
قاعدة بيانات الذكاء الاصطناعي البنّاء داخل KABEERI
هذا الملف يصف قاعدة بيانات AI Co-builder كطبقة بناء وتعديل آمنة داخل Kabeeri. الهدف ليس إضافة Chatbot فقط، بل بناء نظام قادر على اقتراح خطط، معاينة التغييرات، طلب الموافقات، تطبيق التغييرات المسموحة، تسجيل كل شيء، وإنشاء نقاط رجوع قبل أي تغيير مؤثر.
يعتمد هذا الملف على Core Kernel وPermissions وActivity/Audit Logs وFeature Flags وWorkflows، ويخدم CMS وCommerce وERP وRabet وMall وDeveloper Platform وIntegration Hub.
1. الهدف من AI Co-builder Database
هدف قاعدة البيانات هو تمثيل دورة حياة أي طلب AI داخل Kabeeri من أول prompt إلى آخر rollback. لا يكفي حفظ المحادثة؛ يجب حفظ السياق، الخطة، المخاطر، المعاينة، الموافقات، التنفيذ، التكلفة، والأثر على الكيانات.
منع AI من تجاوز صلاحيات المستخدم.
منع أي تعديل حساس بدون Preview + Approval.
تسجيل كل قرار وتغيير في Activity Log و Audit Log عند الحاجة.
توفير Rollback Point قبل التغييرات المؤثرة.
فصل AI Assistant عن AI Co-builder وعن AI Agent وعن AI Skill.
ربط AI usage بالخطط والـ entitlements والتكلفة.
تجهيز V4 Co-builder V1، ثم V5 ERP Assistants، ثم V6 Advanced AI Agents.
2. القاعدة الذهبية
لا يوجد AI Action مباشر وخطير. أي تعديل مؤثر يجب أن يمر بالمسار التالي:
Prompt→ Context Check→ Permission Check→ AI Plan→ Risk Classification→ Preview→ User Approval→ Optional Workflow Approval→ Apply Changes→ Activity Log / Audit Log→ Rollback Point
كل جدول في هذا الملف مصمم لدعم هذا المسار. أي اختصار لهذا المسار يعتبر خطأ معماري، خصوصا في finance وpayroll وlegal documents وidentity documents وpermissions وpackage installation وpublic publishing.

18. Risk Levels
المستوى
الوصف
أمثلة
السلوك المطلوب
Level 1 / Low
اقتراح أو إنشاء draft غير منشور.
SEO title، page draft، product description draft.
Preview + log، وقد يطبق بعد موافقة بسيطة.
Level 2 / Medium
تغيير يؤثر على محتوى منشور أو إعدادات غير حساسة.
تحديث صفحة منشورة، تعديل menu، إنشاء form.
Preview + user approval.
Level 3 / High
تغيير يؤثر على عمليات أو بيانات عملاء.
Workflow، CRM pipeline، checkout settings.
Approval مشدد + rollback point + audit log.
Level 4 / Critical
Finance/legal/permissions/security/identity.
تعديل journal، payroll، legal status، role permissions.
Blocked أو workflow approval متعدد + sensitive logs.
Level 5 / Forbidden
قرارات لا يجب أن ينفذها AI.
توثيق قانوني نهائي، دفع payouts، حذف audit logs.
Deny دائم أو escalate للإنسان.

24. Data Access Rules
AI لا يرى إلا ما يراه المستخدم أو ما تسمح به سياسة النظام.
أي Context Item يجب أن يحمل نتيجة permission check.
البيانات الحساسة ترسل إلى المزود الخارجي فقط إذا كانت السياسة تسمح وبموافقة واضحة.
يجب تطبيق redaction عند التعامل مع payroll وbank accounts وidentity documents وlegal private documents وprivate evaluations.
لا يستخدم AI credentials مباشرة؛ أي tool يحتاج اتصال خارجي يستخدم Integration Hub بسياسات scopes.
أي write action يجب أن يمر عبر Actions/Services الرسمية وليس SQL مباشر.

29. Indexing & Performance
كل الجداول التشغيلية يجب أن تحتوي organization_id أو ترتبط مباشرة بجدول يحتويه.
فهارس أساسية على organization_id + created_at لسجلات الاستخدام والمحادثات والتغييرات.
فهارس على status وrisk_level وplan_type لتسهيل لوحات المراجعة.
لا تحفظ embeddings أو vector data داخل MySQL في البداية إلا كمرحلة لاحقة أو جدول منفصل.
ai_messages قد يكبر بسرعة؛ استخدم retention أو archiving أو summarization لاحقا.
ai_usage_records يجب أن يكون قابلا للتجميع شهريا للخطط والفوترة.
30. Security Requirements
لا API keys لمزودي AI في DB كنص واضح.
كل tool call يكتب بيانات يجب أن يمر بصلاحية واضحة.
كل high/critical action يكتب audit_logs.
دعم rate limits حسب organization/user/feature.
إمكانية تعطيل provider أو model أو skill بسرعة.
إمكانية revocation لأي AI Skill installation.
منع إرسال بيانات حساسة لمزود خارجي إذا policy لا تسمح.
تسجيل IP/user agent للأفعال الحساسة عبر audit_logs عند التنفيذ.

33. Definition of Done
يمكن للمستخدم طلب بناء صفحة أو Form أو Dashboard عبر AI.
يتم إنشاء ai_change_plan ببنود واضحة وتصنيف خطر.
تظهر preview قبل التطبيق.
لا يطبق AI أي تغيير حساس بدون approval.
كل apply ينشئ ai_apply_run وai_applied_changes.

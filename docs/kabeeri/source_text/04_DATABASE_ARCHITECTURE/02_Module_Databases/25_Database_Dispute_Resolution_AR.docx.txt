KABEERI Database File 25 — Dispute Resolution Database
نظام فضّ النزاعات داخل KABEERI
هذا الملف يصف تصميم قاعدة البيانات الخاص بنظام النزاعات الذي يخدم Kabeeri Mall، Commerce، Talent Marketplace، Rabet، Legal Partner Network، Internal Marketplace، Contracts، Billing، وERP.
الهدف ليس بناء شاشة شكاوى بسيطة، بل بناء طبقة تشغيل وحوكمة تمنع فقدان الثقة داخل السوق العام، وتحافظ على الأدلة والقرارات والاعتراضات بشكل قابل للتتبع والتصعيد.
1. لماذا نحتاج Dispute Resolution؟
Kabeeri ليست CMS فقط؛ المنصة تحتوي على خدمات، منتجات، مواهب، توثيق، عقود، فواتير، عمولات، وMarketplace. لذلك أي تعامل قد يتحول إلى خلاف يحتاج مسارًا واضحًا بدل أن ينتشر داخل الرسائل أو المراجعات فقط.
• حماية المستخدمين من الخدمات الوهمية أو المنتجات غير المسلّمة.
• حماية الشركات من تقييمات غير عادلة أو بلاغات كيدية.
• حفظ الأدلة والرسائل والقرارات قبل أي refund أو suspension.
• ربط النزاع بالـ order أو service request أو job offer أو verification request أو contract.
• تغذية Reputation وTrust Score بنتيجة النزاع دون كشف تفاصيل خاصة للعامة.
• تجهيز V5/V6 للـ contracts/disputes وmulti-vendor commerce وenterprise governance.
2. نطاق الملف
هذا الملف يغطي طبقة النزاعات المركزية فقط. لا يكرر جداول Reviews أو Commerce أو Contracts، لكنه يربط بها عبر related_type / related_id وsource references.
• Disputes core lifecycle.
• Dispute parties and roles.
• Messages and evidence.
• Decision, actions, appeals.
• SLA, escalation, assignment.
• Financial holds/refund references.
• Review/reputation impact.
• Moderation and legal escalation links.
• Audit, privacy, export, Portable/Dedicated rules.

4. المبادئ الحاكمة
• كل نزاع يجب أن يرتبط بسياق واضح: organization_id، company_id، وأحيانًا site_id.
• لا يتم حذف النزاعات فورًا لأنها مرتبطة بالثقة، الفواتير، المراجعات، الامتثال، والسجلات القانونية.
• لا يظهر محتوى النزاع للعامة، لكن نتيجته قد تؤثر على Trust Score أو Reputation Score.
• الأدلة تحفظ عبر Media/DMS ولا تخزن كملفات مباشرة داخل جدول النزاع.
• القرارات الحساسة مثل refund أو suspension أو badge removal تمر عبر approval/audit عند الحاجة.
• الطرف الذي يفتح النزاع لا يستطيع التحكم في القرار أو حذف الأدلة بعد إغلاقه.
• الـ moderators يرون فقط النزاعات المسندة لهم أو التي يملكون صلاحية مراجعتها.
• Portable/Dedicated instances لا تنشر تفاصيل النزاع إلى Mall، وإنما ترسل status/summary آمن عند اللزوم.

8. العلاقات مع الأنظمة الأخرى
النظام
العلاقة
Kabeeri Mall
النزاعات ترتبط بـ mall listings, service requests, product inquiries, seller profiles، وتؤثر على visibility/trust عند الحل.
Commerce
النزاع قد يرتبط بـ order/payment/shipping/refund ويفتح financial hold.
Talent Marketplace
النزاع قد يرتبط بـ job offer أو professional profile أو company-to-professional work.
Rabet / Verification
النزاع قد يؤثر على trust record أو verification status عند إثبات احتيال أو مستند مضلل.
Reviews & Reputation
unfair_review disputes يمكن أن تؤدي إلى hide/remove review أو تعديل reputation impact.
Moderation
policy_violation disputes قد تفتح moderation case أو escalate إلى legal review.
Unified Inbox
dispute messages يمكن أن تظهر كconversation محدودة أو تفتح conversation مرتبطة.
Billing
النزاع قد يحجز payout أو commission أو يفتح refund/credit.
Contracts
contract_dispute يستند إلى contract records وcontract parties في ERP Pro.
Documents/DMS
الأدلة الحساسة تحفظ كمستندات ذات صلاحيات، وليس مجرد media عامة.

12. قواعد الخصوصية
• النزاع ليس محتوى عامًا، حتى لو كان مرتبطًا بـ Mall Listing عام.
• الأدلة لا تظهر إلا للأطراف المصرح لهم أو moderators.
• رسائل النزاع لا ترسل إلى Mall Mirror.
• يمكن عرض حالة عامة مثل “dispute rate” أو “resolved dispute” داخل trust signals بدون تفاصيل.
• لا يسمح لطرف بتحميل كل أدلة الطرف الآخر إلا إذا visibility تسمح بذلك.
• المستندات القانونية أو العقود الخاصة تستخدم DMS permissions وليس media visibility العامة.
• حذف حساب المستخدم لا يعني حذف النزاعات المرتبطة بفواتير أو مراجعات أو امتثال.
13. Portable / Dedicated / Frontend Anywhere
الوضع
قاعدة التعامل مع النزاعات
Cloud
النزاعات داخل قاعدة Kabeeri Cloud ويمكن ربطها مباشرة بـ Mall/Commerce/Talent.
Frontend Anywhere
لا تغيير في مصدر النزاع لأن البيانات والـ Control Panel داخل Cloud. الواجهة الخارجية قد تفتح dispute عبر API محدود.
Portable
النزاعات التشغيلية بعد الخروج تبقى في self-hosted DB، لكن النزاعات المتعلقة بـ Mall أو trust يمكن مزامنة status آمن للمنصة المركزية.
Dedicated
النزاعات داخل Dedicated DB، مع bridge مركزي للـ Mall trust signals وsupport/legal escalation عند الاتفاق.
Mall Mirror
لا يحفظ تفاصيل النزاع، فقط مؤشرات آمنة عند الحاجة: dispute_count, dispute_rate, last_resolved_at, trust impact.

21. Acceptance Criteria
• لا يمكن فتح نزاع بدون related object أو وصف واضح وسبب محدد.
• الأطراف يتم إنشاؤهم تلقائيًا من الكيان المرتبط كلما أمكن.
• لا يمكن لطرف رؤية evidence غير مصرح له بها.
• كل تغيير حالة يسجل في dispute_status_history.
• كل قرار مهم ينشئ audit log.
• الإجراءات المالية لا تنفذ بدون صلاحية وقرار واضح.
• يمكن حساب SLA overdue بدقة.
• يمكن تصدير بيانات النزاع الخاصة بالعميل مع احترام retention/legal limits.
• لا تصل تفاصيل النزاع إلى Mall Public أو Frontend Anywhere public APIs.
• النظام يدعم appeal optional بدون كسر القرار الأصلي.
22. الخلاصة التنفيذية
Dispute Resolution في Kabeeri هو طبقة ثقة وحوكمة، وليس مجرد جدول شكاوى. يجب أن يرتبط بالـ Marketplace وMall وCommerce وTalent وRabet وContracts وBilling، وأن يحفظ الأدلة والقرارات والتصعيد والاعتراضات بطريقة قابلة للتدقيق.
القاعدة النهائية: لا سوق عام موثوق بدون Reviews وModeration وDisputes وReputation. وكل نزاع يجب أن يحافظ على الخصوصية، لكنه يترك أثرًا عادلًا على الثقة عند الحاجة.

KABEERI Database File 06 — Integration Between Core, Cloud, Frontend Anywhere, Portable, and Dedicated
ملف التكامل بين الأنظمة الخمسة
هذا الملف يشرح كيف تتكامل الأنظمة الخمسة في Kabeeri:
1. Core Kernel2. Kabeeri Cloud3. Kabeeri Frontend Anywhere4. Kabeeri Portable5. Kabeeri Dedicated
والهدف هو ضمان أن العميل يستطيع الانتقال بين الأوضاع المختلفة بدون فقد بيانات، وأن Kabeeri Mall يظل قادرًا على استقبال البيانات العامة بإذن العميل.
1. الهدف من ملف التكامل
هذا الملف يجيب على:
ما هو النظام الأساسي؟
كيف ينتقل العميل من Cloud إلى Frontend Anywhere؟
كيف ينتقل من Cloud إلى Portable؟
كيف ينتقل من Cloud إلى Dedicated؟
كيف يستمر Kabeeri Mall بعد خروج العميل؟
ما الذي يبقى مركزيًا؟
ما الذي ينتقل للعميل؟
ما هي الجداول المشتركة؟
ما هي جداول الربط؟
كيف نمنع تضارب البيانات؟
2. القاعدة الأعلى
كل الأنظمة تعتمد على Core Kernel.
Core Kernel = مصدر الهوية والملكية والعلاقات الأساسية
لكن مصدر البيانات التشغيلية قد يكون:
Cloud DBأو Dedicated DBأو Portable self-hosted DB
ومصدر البيانات العامة للـ Mall يجب أن يكون:
Mall Mirror داخل Kabeeri Central
3. الأنظمة الخمسة باختصار
3.1 Core Kernel
هوية وملكية وصلاحيات.
3.2 Kabeeri Cloud
كل شيء داخل Kabeeri.
3.3 Frontend Anywhere
الواجهة فقط خارج Kabeeri، والداتا داخل Kabeeri.
3.4 Portable
كل النظام والداتا عند العميل، مع Sync اختياري للـ Mall.
3.5 Dedicated
بيئة مخصصة، غالبًا مُدارة، مع Bridge مركزي.

19. الانتقال من Cloud إلى Frontend Anywhere
مصدر البيانات لا يتغير
يبقى:
Kabeeri Cloud DB
ما يتغير
يتم إنشاء:
frontend_projectfrontend_api_keyfrontend_domainfrontend_webhook
Flow
Cloud site active→ enable Frontend Anywhere entitlement→ create frontend project→ generate scoped API key→ connect external frontend→ keep Mall Sync internal
20. الانتقال من Cloud إلى Portable
مصدر البيانات يتغير
من:
Kabeeri Cloud DB
إلى:
Customer Self-hosted DB
ما يبقى في Kabeeri Central
business_passportmall mirrorbilling relationshipportable licenseself_hosted_installationsync sourcetrust records العامة
Flow
request export→ create export_job→ generate portable bundle→ customer restores externally→ self_hosted_installation registers→ mall_sync_source switches to kabeeri_portable→ cloud operational data archived/deleted by policy
21. الانتقال من Cloud إلى Dedicated
مصدر البيانات يتغير
من:
Shared Cloud DB
إلى:
Dedicated DB
Flow
create dedicated_tenant→ create dedicated_environment→ backup cloud data→ export/import data→ verify→ switch routing/domain→ mall_sync_source switches to kabeeri_dedicated→ cloud status migrated_to_dedicated
22. الانتقال من Dedicated إلى Portable
dedicated export→ portable bundle→ self_hosted_installation registers→ dedicated status migration_out→ mall sync source switches
23. الانتقال من Portable إلى Cloud مرة أخرى
يجب دعمه لاحقًا.
portable instance exports data→ cloud import job→ conflict check→ import into organization→ switch operating mode to cloud_managed→ mall sync source internal again
هذا ليس V1، لكنه يجب أن يكون قابلًا معماريًا.

27. Conflict Rules
27.1 Mall لا يسمح بتجاوز Moderation
حتى لو أرسل العميل تحديثًا من Portable، لا ينشر تلقائيًا إذا كان محتوى حساسًا.
27.2 UUID مهم
الـ UUID يستخدم للمطابقة عبر الأنظمة.
27.3 Source Priority
إذا كان هناك أكثر من مصدر:
cloud_internal أعلى عند Cloudportable_api أعلى عند Portablemanual_admin يمكن أن يتجاوز مؤقتًاmoderation أعلى من الجميع في حالة الإيقاف

40. الخلاصة النهائية
التكامل بين الأنظمة الخمسة يجب أن يعتمد على:
Core Kernel as identity and ownership baseOperating Mode as current runtime stateBusiness Passport as continuing relationshipMall Mirror as public data layerTenant Transitions as controlled migration pathEntitlements as commercial controlAudit Logs as trust layer
القاعدة النهائية:
Kabeeri should let the customer move hosting modes without losing identity, trust, Mall visibility, or data ownership clarity.

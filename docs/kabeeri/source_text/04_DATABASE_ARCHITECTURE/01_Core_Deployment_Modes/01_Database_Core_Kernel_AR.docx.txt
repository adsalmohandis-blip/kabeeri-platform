KABEERI Database File 01 — Core Kernel Database
نظام النواة الأساسية التي سيعمل عليها كل شيء
هذا الملف يصف قاعدة بيانات النواة الأساسية لمنصة KABEERI، وهي الطبقة التي تعتمد عليها كل الأنظمة الأخرى:
Kabeeri CloudKabeeri Frontend AnywhereKabeeri PortableKabeeri DedicatedKabeeri Mall SyncERPCMSCommerceRabetAIMarketplace
النواة ليست Module اختياريًا.
النواة هي أساس المنصة بالكامل.
1. هدف Core Kernel
هدف النواة الأساسية هو توفير:
هوية المستخدمين.
ملف العميل.
تعدد المؤسسات.
تعدد الشركات.
تعدد المواقع.
الصلاحيات.
الإعدادات.
التسجيلات.
الملفات.
التفعيل التجاري للخصائص.
قابلية التصدير.
قابلية الاستضافة الخارجية.
قابلية الربط مع Kabeeri Mall.
القاعدة:
أي Module في Kabeeri يجب أن يعرف: يتبع أي Organization؟ أي Site؟ أي Company؟ وأي User فعل التغيير؟
2. المفهوم الأعلى للبيانات
Kabeeri يجب أن يبدأ من ملف العميل وليس من الموقع.
الترتيب الصحيح:
User→ Organization / Customer Account→ Company / Business Account→ Site / Store / Portal→ Business Profile→ Mall Listing→ Modules / ERP / Commerce / AI
3. Core Ownership Model
3.1 User
الشخص الحقيقي الذي يدخل المنصة.
3.2 Organization
ملف العميل أو الـ Tenant الأساسي.
يشبه ملف العميل في البنك.
3.3 Company
ملف بزنس أو شركة داخل حساب العميل.
يشبه الحساب التجاري داخل ملف العميل البنكي.
3.4 Site
واجهة رقمية أو قناة نشر تابعة للـ Organization، وقد ترتبط بـ Company.
3.5 Business Profile
الملف العام للبزنس، وهو الذي يمكن أن يظهر في Kabeeri Mall.
4. مبادئ تصميم قاعدة بيانات النواة
4.1 Tenant Scoped
كل بيانات العميل يجب أن تكون مرتبطة بـ:
organization_id
وعند الحاجة:
site_idcompany_id
4.2 Portable
كل بيانات العميل يجب أن تكون قابلة للتجميع والتصدير.
4.3 Modular
كل Module يضيف جداوله، لكنه يلتزم بنفس قواعد النواة.
4.4 Auditable
كل حدث مهم يجب أن يترك أثرًا.
4.5 Economical
نبدأ بـ:
Shared Database + Tenant Scoping
ولا نبدأ بـ Database لكل عميل من اليوم الأول.
5. أنواع الجداول في النواة
5.1 Global Platform Tables
جداول عامة للمنصة كلها.
أمثلة:
countries.
currencies.
global permissions.
platform plans.
global package catalog.
5.2 Tenant Tables
جداول تخص العميل.
كلها يجب أن تحتوي organization_id أو تكون مرتبطة بجدول يحتويه.
5.3 Public Mirror Tables
جداول عامة للعرض في Kabeeri Mall، لا تساوي قاعدة بيانات العميل الأصلية.
5.4 Derived Tables
جداول مشتقة للتقارير أو الكاش، ويمكن إعادة بنائها.

34. قواعد Tenant Isolation
34.1 كل Query في Admin يجب أن تحتوي Scope
مثال:
where organization_id = currentOrganizationId
34.2 ممنوع الاعتماد على UI فقط
العزل يجب أن يكون في:
Policies.
Query scopes.
Services.
Tests.
34.3 اختبارات إلزامية
User from organization A cannot view organization B dataUser from company A cannot manage company B dataSite admin cannot access unrelated site
35. Tenant Export Readiness في النواة
النواة يجب أن تجهز الجداول التالية، حتى لو التنفيذ الكامل لاحقًا:
export_jobstenant_export_itemsexport_manifests
لكن تفاصيلها في ملف Portable.
36. Mall Sync Readiness في النواة
النواة يجب أن تسمح بربط:
organizationcompanybusiness_profilesite
بـ Mall Mirror لاحقًا.
أي Business عام يجب أن يكون له:
public identitysource ownervisibilitypublication status

40. Core Kernel Release Requirements
النواة تعتبر جاهزة عندما:
User can register/loginOrganization can be createdUser can join multiple organizationsCompany can be created under organizationSite can be created under organizationRBAC worksSettings workFeature flags workMedia storage is tenant-scopedActivity logs workAudit logs workModules can be registered and installedTenant isolation tests pass
41. الخلاصة
Core Kernel هو أساس Kabeeri.
أي خطأ في النواة سيؤثر على:
Cloud.
Portable.
Dedicated.
Frontend Anywhere.
Mall Sync.
ERP.
AI.
Security.
القاعدة النهائية:
لا تبدأ Modules ضخمة قبل أن تكون النواة مستقرة، معزولة، قابلة للتصدير، وقابلة للتدقيق.
